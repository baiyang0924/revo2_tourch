# 14 · 模型拼接与复合动作编排

> 本文解决三个问题：
> 1. ELF3 本体模型（31 关节，不含手）+ Revo2 灵巧手模型，如何组成统一的仿真模型？
> 2. 臂与手能否由单条命令统一控制？还是需要分离的两条通道？
> 3. 两个通道如何编排为一个复合动作？
>
> **结论**：应采用「两条独立通道 + 上层编排器」的架构，而非合并为单一程序。
> 这不是折中方案，而是由两条控制通路的物理独立性决定的 ——
> 臂与手在数据链路上没有交集，真机不存在「合并为单一程序」的可行性。
>
> **本文侧别约定**：本项目 ELF3 实机装配的是**右手**（右腕 `r_wrist_z_link`，
> CAN6 / ID 127）。下文所有关节名、挂载点、命令示例均以右手为准。
> 官方左右手模型结构完全对称，仅前缀 `right_` / `left_` 不同，
> 需要切左手时把 `right_` 换成 `left_`、`r_wrist_z_link` 换成 `l_wrist_z_link` 即可。

## 1 · 官方手模型长什么样（原文核对结果）

### 1.1 结构（右手）

```
right_hand_base_link                   ← 根 body（挂载点，无 pos/quat，默认在原点）
├── right_thumb_metacarpal_link        ← 拇指·掌骨
│   └── right_thumb_proximal_link      ← 拇指·近节
│       └── right_thumb_distal_link    ← 拇指·远节
├── right_index_proximal_link          ← 食指·近节
│   └── right_index_distal_link        ← 食指·远节
├── right_middle_proximal_link         ← 中指（同上）
├── right_ring_proximal_link           ← 无名指（同上）
└── right_pinky_proximal_link          ← 小指（同上）
    每指末尾还挂 _tip_link 与 _touch_link（空 body，触觉点占位）
```

### 1.2 关节（MJCF 原文，11 个 hinge）

| # | 关节名 | axis | range (rad) | 力矩限 | 对应人的动作 |
|---|---|---|---|---|---|
| 0 | `right_thumb_metacarpal_joint` | `0 0 1` | 0 – **1.57** | ±0.5 | 拇指对掌/外展 |
| 1 | `right_thumb_proximal_joint` | `-1 0 0` | 0 – 1.03 | ±1.1 | 拇指近节弯 |
| 2 | `right_thumb_distal_joint` | `-1 0 0` | 0 – 1.03 | ±1.1 | 拇指远节弯 |
| 3 | `right_index_proximal_joint` | `0 1 0` | 0 – **1.41** | ±2.0 | 食指近节 |
| 4 | `right_index_distal_joint` | `0 1 0` | 0 – 1.63 | ±2.0 | 食指远节 |
| 5 | `right_middle_proximal_joint` | `0 1 0` | 0 – 1.41 | ±2.0 | 中指近节 |
| 6 | `right_middle_distal_joint` | `0 1 0` | 0 – 1.63 | ±2.0 | 中指远节 |
| 7 | `right_ring_proximal_joint` | `0 1 0` | 0 – 1.41 | ±2.0 | 无名指近节 |
| 8 | `right_ring_distal_joint` | `0 1 0` | 0 – 1.63 | ±2.0 | 无名指远节 |
| 9 | `right_pinky_proximal_joint` | `0 1 0` | 0 – 1.41 | ±2.0 | 小指近节 |
| 10 | `right_pinky_distal_joint` | `0 1 0` | 0 – 1.63 | ±2.0 | 小指远节 |

> 上位机侧（`config/revo2_model_map.yaml`）另存有一份完整对照，含每条映射的
> `confidence` 与 `mismatch` 说明，是后续代码的唯一权威依据。

### 1.3 官方文件缺失项 —— 需自行补充

| 缺什么 | 原文证据 | 后果 |
|---|---|---|
| **没有 `<actuator>`** | 全文无该标签，`nu = 0` | 仿真里手不会动，必须自己写执行器 |
| **没有 `<keyframe>`** | 全文无该标签 | 没有预设初始姿态，qpos 全 0 |
| **没有 `meshdir`** | `<compiler>` 只有 `angle/autolimits/balanceinertia` | 靠 `../meshes/...` 相对路径，**目录结构不能拆** |
| **MJCF 里没有 `<mimic>`** | 11 个关节全部无 mimic | 与官方自己的 URDF 矛盾，见下 |

**官方自己在 README 里明说这部分还没做完**（原文照录）：

> Planned or ongoing work includes: **MJCF actuator definitions and
> control-ready simulation settings.**

→ 即：**官方仅提供模型描述，未提供驱动定义。使其可用于仿真的执行器配置需自行实现。**

### 1.4 ★ 官方 URDF 与 MJCF 自相矛盾（必须知道）

同一个官方仓库，同一个手，两种格式给出**两种动力学语义**：

| | URDF 原文 | MJCF 原文 |
|---|---|---|
| 四指 distal | `<mimic joint="right_index_proximal_joint" multiplier="1.155"/>` → **从动** | 独立 hinge，无 mimic → **主动** |
| 拇指 distal | `<mimic joint="right_thumb_proximal_joint" multiplier="1.0"/>` → **从动** | 独立 hinge → **主动** |
| 有效自由度 | **6 个**（1 拇指 metacarpal + 1 拇指 proximal + 4 指 proximal） | **11 个** |

**这个矛盾不是小事**，因为它直接决定「仿真和真机像不像」：

- 真机协议层只有 **6 个可发角度**（`revo2_commander.py` 里 `MOTOR_ORDER` 就是 6 个）；
- 若仿真按 MJCF 放开 11 个，**仿真能做出真机物理上做不到的手指姿势**；
- 后果：仿真中调试完成的抓取动作，在真机上无法复现手指姿态 → 前期调试失效。

**处理原则（写进 `config/revo2_model_map.yaml` 的 M2 条）**：

> 仿真里也把 distal 锁成从动（补 `<mimic>` 或用 `<equality>` 约束），
> 让仿真的有效自由度 = 6，与真机一致。**仿真要模拟真机，不是超越真机。**

`tools/revo2_make_actuated.py` 已实现这一步（见 §3 方案 B'）。

## 2 · 关键差异：本仓库 6 电机编号与官方 11 关节不对应

`config/gestures.yaml` 定义的 6 个电机编号如下：

```
[拇指Flex, 拇指Aux, 食指, 中指, 无名指, 小拇指]   上限见 `config/revo2_hardware.yaml`（[59.0, 89.0, 80.8, 80.8, 80.8, 80.8]）
```

拿这套名字去官方模型里找对应关节，**三条对不上**：

### M1 · 「拇指Aux」在官方模型里找不到同名关节

官方拇指只有 `metacarpal` / `proximal` / `distal` 三个。按物理含义，
「Aux（对掌外展）」最接近 `metacarpal`，而且——

> `metacarpal` 的 `range` 上界是 `1.57 rad` = **90.0°**
> 本仓库 `gestures.yaml` 对「拇指Aux」设定的上限同为 **90°**

数值巧合到这种程度，**很可能就是它**。但这是推断，不是官方给出的映射。
**接真机后第一件事就是单独给 `metacarpal` 一个角度，看实际动的是哪个方向。**

### M2 · 四指 distal 关节在本仓库侧无对应电机编号

官方模型每指 2 个关节，本仓库每指仅 1 个电机编号。其中：

> 官方 `index_proximal` 的 `range` 上界 `1.41 rad` = **80.8°**
> 本仓库对「食指」设定的上限为 **81°**

**完全吻合**（1.41 rad ≈ 80.79°，取整 81）。可见本仓库的 81° 源自官方该限位，
因此 `食指 → index_proximal` 的映射**可确认**。
中指/无名指/小指同理。

而 `distal`（0–1.63 rad = 93.4°）在本仓库侧无独立电机编号 →
印证了 §1.4：**真机上 distal 是内部耦合的，不单独控制。**

### M3 · 汇总：真机 6 通道 vs 模型 11 关节

```
真机可命令：  6 个（拇指Flex, 拇指Aux, 食指, 中指, 无名指, 小拇指）
模型可动：   11 个（拇指 3 + 四指 × 2）
差额 5 个 = 4 指 distal + 拇指多出的 1 个 → 真机内部耦合，不可单独命令
```

**→ 这就是为什么仿真必须锁 distal：让仿真的自由度也等于 6。**

> 完整对照表（含 confidence 与 action）已写成
> `config/revo2_model_map.yaml`，那份文件是后续所有代码的**唯一权威依据**。
> 其状态标记为 `UNVERIFIED`，需完成真机标定后方可置为 `verified: true`。

## 3 · 怎么把两个模型拼成一个（仿真侧）

三种方案，按推荐度排序。

### 方案 A · 运行时 attach 挂载（MuJoCo 3.1+）

MuJoCo 3.1 引入了 `MjSpec.attach()`，可以在内存里把一份 spec 挂到另一份上：

```python
import mujoco

elf3 = mujoco.MjSpec.from_file("elf3_dof31/scene.xml")
hand = mujoco.MjSpec.from_file("revo2_system/mjcf/revo2_right.xml")

# 把右手整棵树挂到右腕上，前缀 right_
frame = elf3.body("r_wrist_z_link")
elf3.attach(frame, hand, prefix="right_")

model = elf3.compile()
```

**优点**：不改官方文件，脚本里几行就完成。
**缺点**：官方手模型缺 actuator，attach 进来还是不会动，仍要自己补；
且 meshdir 解析要单独处理。

### 方案 B · 离线合并成一个 XML（**起步推荐**）

把 `revo2_right.xml` 的 body 树整段拷进 ELF3 的手腕 body 下，产出一个自包含文件：

```
data/mujoco_simulation/
├── elf3_dof31/                ← 官方本体（31 关节，不含手）
└── elf3_both_hands.xml        ← ★ 本项目合并产物（本体 + 双手）
```

合并时要做的 6 件事：

1. **改挂载点**：把 `<body name="right_hand_base_link">` 整段移到
   `r_wrist_z_link` 的 body 内部，作为子 body。
2. **统一 meshdir**：ELF3 与 Revo2 的 mesh 在不同目录 →
   把两边的 mesh 汇总到一个 `meshes/` 下，或在 `<compiler meshdir="...">` 里指定；
   官方手模型用的是 `../meshes/hands/{visual|collision}/{left|right}/*.STL` 相对路径，
   **迁移时必须保持这个相对层级**，否则 MuJoCo 报 mesh 找不到。
3. **合并 `<asset>`**：两边的 `<mesh>` 段拼起来（名字不会冲突，官方用了长前缀）。
4. **补 `<actuator>`**（★ 官方缺的就是这个）：
   ```xml
   <actuator>
     <position name="thumb_metacarpal_pos" joint="right_thumb_metacarpal_joint"
               kp="2.0" kv="0.1" ctrlrange="0.0 1.57"/>
     <position name="thumb_proximal_pos" joint="right_thumb_proximal_joint"
               kp="2.0" kv="0.1" ctrlrange="0.0 1.03"/>
     <!-- 四指 proximal 各一条 -->
   </actuator>
   ```
   `kp/kv` 官方没给 → 按 `actuatorfrcrange` 量级试（拇指 ±0.5 Nm、四指 ±2 Nm）。
5. **锁 distal 为从动**（§1.4）：给 4 个 distal 加 `<equality>` 约束，
   或改关节类型让其跟随对应 proximal（URDF 的倍率是 1.155 / 1.0）。
6. **更新 torso/骨架位置**：合并后 `nq` 从 31 变 31+11×N。

**优点**：产物是一个文件，后面所有调试都简单；版本可控、可比对。
**缺点**：一次性体力活，且官方更新模型后要重做。

### 方案 B' · 用脚本自动做第 4、5 步（**已写好并实测**）

`tools/revo2_make_actuated.py` 就是方案 B 里最繁琐的两步（补 `<actuator>` +
锁 distal）的自动化实现。**已用官方原始文件实测通过，并支持左右手自动判侧。**

```bash
# 1. 先看会改成什么（不写文件）
python3 tools/revo2_make_actuated.py revo2_system/mjcf/revo2_right.xml --dry-run

# 2. 真的生成
python3 tools/revo2_make_actuated.py revo2_system/mjcf/revo2_right.xml
# → 产出同目录下 revo2_right_actuated.xml

# 3. 换增益（官方没给 kp/kv，默认拇指 2.0、四指 4.0）
python3 tools/revo2_make_actuated.py revo2_right.xml --kp-thumb 2 --kp-finger 4

# 4. 不想锁 distal（保留 11 自由度，不推荐，见 §1.4）
python3 tools/revo2_make_actuated.py revo2_right.xml --no-mimic
```

**侧别处理**：脚本按关节名前缀工作，默认自动判侧
（先看关节名，再看文件名），两侧结构对称所以同一套代码通用。
换左手时无需改代码，直接传左手文件即可：

```bash
# 自动判出是左手
python3 tools/revo2_make_actuated.py revo2_system/mjcf/revo2_left.xml
# 或显式指定（与模型实际侧别不符会直接拒绝，退出码 2）
python3 tools/revo2_make_actuated.py revo2_left.xml --side left
```

**实测结果**（2026-09-22，官方 `revo2_right.xml` 原文）：

| 项 | 输入 | 输出 |
|---|---|---|
| `<actuator>` | 无 | **6 个 position 执行器** |
| `<equality>` | 无 | **5 条 distal 跟随约束**（四指 ×1.155、拇指 ×1.0） |
| hinge 关节 | 11 | 11（保留，但 distal 被约束住） |
| 有效驱动自由度 `nu` | 0 | **6** ✅ |

脚本自带四道安全设计：

- **幂等**：重复跑不会叠加 actuator（已测：连跑两次仍是 6 个）
- **防误覆盖**：输出已存在时拒绝写入，退出码 3，需 `--force`（已测）
- **结构校验**：先核对 6 个主动关节是否都在，`range` 与文档记录不一致会告警
  （官方若更新模型，这里能立刻发现）
- **侧别交叉核对**：`--side` 与模型里的关节名前缀不符时直接拒绝，
  避免把右手执行器写进左手模型（已测）

> ⚠️ 脚本只做**纯文本 XML 变换**，不加载 MuJoCo、不发指令、不碰硬件。
>
> ⚠️ `kp/kv` 是**按力矩量级估的**，官方没给值。首次真机从小往大试。
> 估算逻辑写在脚本 `suggest_gains()` 里，可读可改。

### 方案 C · 两个仿真各跑一半（不推荐）

一个进程跑 ELF3 本体，另一个只跑手，用话题对齐。

**为什么不行**：手和臂之间**没有物理约束关系**。抓取的本质是
「手指与瓶身的接触力」+「手臂把瓶子顶住」的联合效果。
分成两个仿真后，接触力算不出来 → **抓瓶验证等于没做**。

> 只在一种情况下用：**只想单独看手型对不对**（手在空中的姿态）。
> 对应 `docs/13` M1 阶段任务（确定抓取手型），
> 那时可以只跑手的 MJCF，不必合并。

### 决策建议

| 阶段 | 用什么 | 理由 |
|---|---|---|
| M1 定手型 | **方案 C**（只跑手） | 手型对不对和臂没关系，省去合并 |
| M2 臂到位 | 官方 elf3 本体（不含手） | 臂不碰手，用官方 launch 就行 |
| **M3 联合抓取** | **方案 B** | 必须算接触力，必须合并 |
| 长期维护 | 方案 A | 官方模型更新后不用重做手工合并 |

**→ 先做 M1/M2，等真正要「臂+手一起抓瓶」时再上方案 B。**
不宜初期即执行模型合并。在手型与臂位姿均未验证的阶段合并模型，
一旦出现问题将无法区分是模型缺陷还是参数错误。

## 4 · 控制侧：先两条命令（这是对的路）

### 4.1 为什么必须分两条：两条通路在物理上就是独立的

| | 臂 | 手 |
|---|---|---|
| 通路 | ROS 2 话题 `actuators_cmds_override` | CANFD `/canfd_packet/rx|tx` + `bc-stark-sdk` |
| 寻址 | **按关节名**（`actuators_name` 数组） | **按总线 + ID**（右手 CAN6/127、左手 CAN5/126） |
| 时效 | **0.2 s 覆盖超时 → 必须 ≥5 Hz 持续发** | **发一次就保持** |
| 谁发 | `tools/arm_pose_pub.py` | `src/elf3_ros2/revo2_commander.py` |
| 运行位置 | 开发机 | commander 运行于开发机；bridge 运行于机器人（占用主控板 CAN） |

**两个系统的数据通路从头到尾没有交集** —— 不可能「合并成一个程序」。
所谓「一条命令」，本质上只能是一个**编排器**：它同时扮演两个客户端，
按正确时序分别发令。这就是第三层「组合成新命令」的真实含义。

### 4.2 两条现成命令（先各自跑通）

**臂**（先空转/仿真，别上真机）：

```bash
# 只看会发什么，不真发
python3 tools/arm_pose_pub.py zero --dry-run

# 仿真里发
python3 tools/arm_pose_pub.py zero --topic-prefix simulation

# 真机发右臂（工具按关节名寻址，--sides 选哪只臂）
python3 tools/arm_pose_pub.py zero --topic-prefix hardware --i-know-its-real \
    --sides right --rate 20 --seconds 5
```

**手**（本项目为右手，只打印，不真发）：

```bash
# 回零位预览
python3 src/elf3_ros2/revo2_commander.py angles 0,0,0,0,0,0 --hand right --print-only

# 发一个手势
python3 src/elf3_ros2/revo2_commander.py gesture open --hand right
```

**⚠️ 三条必须知道的硬事实：**

1. **手上位机 `duration_ms` 上限是 2000 ms**（`revo2_commander.py` 里
   `DURATION_MIN, DURATION_MAX = 1, 2000`）。
   → 想做 3 秒的慢动作，**必须在序列里拆成多步**，不能写一个 3000。
2. **臂的覆盖 0.2 s 超时**：发一次就不管了，臂会在 0.2 s 后失效回弹。
   → 任何复合动作里，臂必须**全程 ≥5 Hz 持续发**，`arm_pose_pub.py` 已经在
   发布循环里保证了这点（`min_publish_rate_hz: 5`）。
3. **真机落地前必须先进入不靠手臂维持平衡的状态**（`com.bxi.basic_actions/hello`
   或 `applause`）。平衡策略正用臂配重，直接抢过来会摔。
   吊装时只能用 `initial_pos` / `pd_brake`。这条是 `docs/13` §5 的红线第 1 条。

### 4.3 时序铁律：臂先到位，手再闭合

这是整个复合动作里**唯一不能错**的一条：

```
t0 ──── 臂开始移动 ────→ t1 臂到达抓取位 ────→ t2 手开始闭合 ──→ t3 手闭合完成
         (≥5 Hz 持续发)       ▲ 到位判定            (发一次即保持)
                              │
                        必须等臂稳定
```

**为什么**：如果手先闭合、臂还在动，手会先抓住空气，
然后臂带着一个闭合的手移过去 → 撞瓶、或者抓空。
反过来（臂先到位）最多是手慢一点碰上去，安全得多。

**现有资产已经能表达这个时序** —— `src/elf3_ros2/config/sequences.yaml`
里已经有 `robot_sync: true` 和每步的 `robot_phase` 字段，
`递物综合` 序列就是这种写法。**不要另起一套。**

## 5 · 编排层：组合成一条新命令

### 5.1 设计：给 `arm_pose_pub.py` 加一个编排子命令

不要新写一个脚本。在已有的 `tools/arm_pose_pub.py` 上加
`grasp_pick_bottle` 子命令，里面按阶段调用：

```
阶段 0  安全检查       → 进 hello/applause，确认平衡交给动作状态机
阶段 1  手臂到 pre_grasp → 复用 config/arm_poses.yaml 的 pre_grasp 位姿
阶段 2  手张开到位      → 复用 gestures.yaml 的 open
阶段 3  手臂到 grasp_close → 复用 grasp_close 位姿
阶段 4  手闭合握持      → 复用 gestures.yaml 的 bottle_grasp（1200 ms）
阶段 5  手臂到 lift     → 复用 lift 位姿
阶段 6  保持 + 松开     → 按需
```

**关键设计原则**：

- **复用已有位姿与手势，不新建**。`arm_poses.yaml` 里 `pre_grasp` /
  `grasp_close` / `lift` 已经有了（虽然 `left/right` 还是 `null` 待填 IK，
  本项目先填 `right`）；`gestures.yaml` 里 `bottle_grasp` 已经有了。
  → 编排器只负责**排顺序 + 卡时间**，不负责定义姿态。
- **每个阶段只做一件事**，失败能定位到具体阶段。
- **每阶段之间加显式等待**，等臂到位再动手（§4.3）。
- **随时可中断**：每阶段开头打印当前阶段名，方便 Ctrl+C。

### 5.2 现成的模板：`sequences.yaml` 里的 `抓取圆柱`

这份手部序列已经是抓瓶的原型，结构可以直接借：

```yaml
抓取圆柱:
  description: 张开 → 前伸就位 → 闭合握持 → 保持 → 松开
  steps:
    - name: 张开准备
      angles: [0, 0, 0, 0, 0, 0]
      duration_ms: 1000
    - name: 预备位
      angles: [20, 30, 25, 25, 25, 25]
      duration_ms: 1000
    - name: 闭合握持
      angles: [45, 60, 60, 60, 60, 60]
      duration_ms: 1200
    - name: 保持
      angles: [45, 60, 60, 60, 60, 60]
      duration_ms: 2000      # ← 注意：正好卡在 2000 ms 上限
    - name: 松开
      angles: [0, 0, 0, 0, 0, 0]
      duration_ms: 1200
```

> **注意「保持」那步是 2000 ms** —— 正好是协议上限。
> 若要「保持 5 秒」，必须写成多步重复，不能写 5000。

### 5.3 复合动作的推荐写法

扩展现有的 `sequences.yaml` 结构（**沿用 `robot_sync` / `robot_phase`**）：

```yaml
抓取水瓶:
  description: 臂先到位、手再闭合，全流程 6 阶段
  robot_sync: true
  steps:
    - name: 手张开
      angles: [0, 0, 0, 0, 0, 0]
      duration_ms: 800
      robot_phase: "arm:pre_grasp"       # 臂同时奔向 pre_grasp
    - name: 等待臂到位
      angles: [0, 0, 0, 0, 0, 0]
      duration_ms: 1200
      robot_phase: "arm:hold"            # 臂保持，等稳定
    - name: 闭合并抓
      angles: [45, 60, 60, 60, 60, 60]
      duration_ms: 1200
      robot_phase: "arm:grasp_close"     # 手闭合时臂已在抓取位
    - name: 抬升
      angles: [45, 60, 60, 60, 60, 60]
      duration_ms: 1500
      robot_phase: "arm:lift"
```

**`robot_phase` 的语义**：告诉编排器「这一步执行时，臂该处在哪个位姿」。
编排器读到 `arm:pre_grasp` 就去 `arm_poses.yaml` 取 `pre_grasp` 并持续发。

## 9 · 端到端仿真：右手拿起瓶装水并递出（已跑通）

本节记录 M3 的仿真侧验证结果，以及过程中确认的两个**模型层缺陷**。

### 9.1 产物与命令

| 项 | 内容 |
|---|---|
| 模型 | `elf3_revo2_right.xml`（`nq=56 nv=54 nu=37 nbody=55`；本体 31 + 右手 6 执行器） |
| 脚本 | `tools/revo2_pick_bottle_demo.py` |
| 命令 | `python3 tools/revo2_pick_bottle_demo.py --model <dir>/elf3_revo2_right.xml --mode combo --record out/` |
| 三个模式 | `--mode arm` 只动手臂 / `--mode hand` 只动手 / `--mode combo` 完整序列 |
| 实测结果 | 瓶子最大抬升 **372.9 mm**，最终高度 283.3 mm，手部最大跟踪误差 6.9° |
| 退出码 | 0 正常 / 1 用法或模型问题 / 5 动作未完成（瓶子未提起 ≥ 40 mm） |

### 9.2 动作序列（8 阶段）

```
approach 抬起           手臂抬到工作区上方，手张开
approach 平移到瓶子上方  水平移动到瓶子上方 180 mm
descend 下降到抓取高度   垂直下降
grasp 手闭合            6 个手部执行器到抓握角，四指 distal 由 equality 跟随
lift 抬起               垂直上升 140 mm
handover 递给对方        前伸抬高到递交位
release 张开手
retract 收回
```

**时序铁律**（§4.3 的仿真侧复现）：手臂到位与手闭合必须分属两个阶段。
若手先闭合而手臂仍在运动，闭合的手会带着空握姿态扫过目标。

### 9.3 纯力矩 PD 的稳态误差必须用外环补偿

ELF3 官方 MJCF 的 31 个本体关节是**纯力矩 `<motor>`，无重力补偿**。
直接下发 IK 解算出的关节角，手臂受自重影响会稳定在目标点下方约
**50~110 mm**，抓取位不可达。

处理方式（`solve_reachable_arm()`）：

```
第 n 轮：指令 = 目标 + 累计误差补偿  →  PD 跑至收敛  →  测量实际手根位置
        误差 = 目标 − 实际  →  累加回下一轮指令
```

实测收敛（抓取位）：`67.6 → 14.4 → 3.1 → 0.5 mm`，4 轮进入亚毫米级。
配发散保护：单轮误差超过历史最优的 1.6 倍 + 15 mm 即判定被环境卡住，
回退至最优轮并终止。

**该误差在真机上不存在** —— 真机伺服带重力补偿。这是纯仿真环境的补偿项。

### 9.4 ★ 官方手碰撞网格与 Ø65 mm 瓶不兼容（模型层缺陷）

**现象**：闭合的手与瓶接触时，瓶子被弹飞。
**量化**：以 `mj_geomDistance` 测量，握紧状态下
`right_index_proximal_link_collision_0` 与瓶面**互相嵌入约 39.8 mm**；
张开、半蜷、握紧三种手型均存在嵌入。手掌碰撞网格 AABB 半宽
`[0.0199, 0.0373, 0.049] m`。

**判定**：这是**碰撞网格尺度问题，不是控制参数问题**。
深度嵌入会让接触求解器输出极大的分离力，调增益、调手型、
调摩擦系数均无法解决。

**处理方式**：将「抓取」这一物理事件在仿真中用刚性夹持替代，其余全部保持真实。

| 阶段 | 处理 |
|---|---|
| 抬起、平移、接近 | **真实**：真动力学、真接触、真重力。此阶段撞飞瓶子即代表方案有问题 |
| 下降、合拢 | 目标瓶定位于设计位且关闭碰撞（避免被手推离，实测未处理时被推离 95 mm） |
| 合拢完成瞬间 | 记录「手根→瓶」固定相对位姿，瓶子随手根运动 |
| 搬运过程 | 位置跟随手根，**姿态固定为锁定时的竖直姿态**（见下） |
| 松手瞬间 | 解除夹持 |

**搬运姿态必须锁定为竖直**：完全刚性跟随手根时，手根 Y 轴在抬臂过程中
偏离竖直最大 **13°**，瓶子随之倾斜，视觉上等同于倾倒液体。真机端此项由
腕关节轨迹规划保证，仿真侧以姿态锁定代替。可用 `--carry rigid` 关闭以观察差异。

**该替代项的边界**（不得据此判断真机能力）：

- ✅ 可信：手臂轨迹、桌板接触、6 个手关节角度及跟踪误差
- 🔧 替代：**抓握本身的力学**。真机依靠摩擦与手指抓握力，仿真依靠刚性约束

对照实验命令：`--grip contact` 保留纯接触抓取，可复现瓶子被弹飞的现象。

### 9.5 两处几何决定

**（1）瓶子位置由「实际手根位姿」反推，而非先摆瓶子再解 IK。**
IK 残余误差与 PD 稳态误差叠加后，手会恰好够不到设计位置的瓶子。
故流程取反：先确定舒适的抓取手型 → 用 IK + 外环标定使手真正到达该位姿 →
以该位姿反推瓶子应摆放的世界位置。
瓶轴在手根坐标系中的位置 `BOTTLE_AXIS_IN_HAND = [0.001, 0, 0.085] m`
由「五指指尖到轴距离等于瓶半径」拟合得到，平均偏差 1.3 mm、最大 2.0 mm。

**（2）桌子为环境常量，一经确定即冻结。**
曾出现循环依赖：瓶子位置由实际手根反推，桌子位置又跟随瓶子。
瓶子微调 12 mm 即导致桌板移到手臂起始位下方，标定发散至 **819 mm**。
现固定桌子中心，流程中仅移动瓶子。

### 9.6 世界坐标侧的已知限制

| 限制 | 说明 |
|---|---|
| 基座钉死 | 每步将基座位姿写回、速度清零，腰/腿/头关节保持零位。手臂与手为真动力学，全身平衡不参与 |
| 无第二人模型 | `--release hold`（默认）使瓶子停在交接点，代表已由对方接住。`--release drop` 恢复自由落体 |
| 递交位横向约束 | 递交目标点的手根 y 分量不得向身体中线移动：瓶体自掌心外伸 85 mm，向中线移动会使瓶体插入躯干。当前递交偏移量为 `(+0.12, −0.01, +0.30) m` |

### 9.7 ★ Windows 平台限制：MuJoCo 无法打开非 ASCII 路径

`mujoco 3.14.0` / Windows 实测：

```
os.path.isfile(r"D:\Desktop\机器人实习\...\elf3_revo2_right.xml")  → True
mujoco.MjModel.from_xml_path(同一路径)  → ValueError: ParseXML: Error opening file '...'
```

进程内路径字符串经核对为正确 Unicode，Python 文件接口可正常访问，
MuJoCo 内部 XML 加载失败，报错回显为乱码。

**结论**：Windows 上模型目录必须置于纯 ASCII 路径（如 `D:\sim\`）。
Linux 不受影响。二者均为 UTF-8 路径，仅供 Windows 侧使用。

### 9.8 ★ 跨平台复现验证（Linux / 仿真工作站）

同一模型、同一参数，在 `172.16.10.133`（Ubuntu 22.04 / ROS 2 Humble）上重跑，
三项验收指标与 Windows 侧逐项一致：

| 指标 | Windows | `.133`（Linux） | 差异 |
|---|---|---|---|
| 瓶子最大抬升 | 372.9 mm | **372.9 mm** | 0 |
| 瓶子最终高度 | 283.3 mm | **283.3 mm** | 0 |
| 手部最大误差 | 6.9° | **6.8°** | 0.1°（浮点差） |

外环标定收敛曲线同样复现：`67.6 → 14.4 → 3.1 → 0.5 mm`（第 5 轮未打印，即已达标提前退出）。
日志结尾自动判定与 Windows 侧一致：`✅ 动作完成：瓶子被抓起并递出`。

**结论：Windows 侧调好的方案可直接搬到 Linux 侧，指标可复现。**

**迁移的实际障碍在打包环节，不在 MuJoCo。**
Windows 侧模型路径含中文（`灵巧手/仿真模型/`），本地打包前须先归档到纯 ASCII 暂存目录，
再以 `tar czf - | ssh 'tar xzf -'` 流式传输；落地后 Linux 侧不受 §9.7 所述路径限制。

一键复现脚本置于工作站 `~/elf3-revo2-work/run_demo.sh`：

```bash
bash ~/elf3-revo2-work/run_demo.sh          # 默认 combo（臂 + 手完整动作）
bash ~/elf3-revo2-work/run_demo.sh arm      # 只验手臂轨迹
```

脚本会在结尾自动提取「最大抬升 / 最终高度 / 手部误差」三项与 `✅/❌` 判定，
**验收一律以这三项数值为准，不以录像观感为准**。
