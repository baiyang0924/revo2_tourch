## 0. 结论摘要

M0 通过。四项判据全部满足，并额外实测出两条官方文档未载明的参数。

| 判据 | 内容 | 实测 | 结果 |
|---|---|---|---|
| A | 点名关节跟到目标 | `r_shoulder_y` 残差 0.0168 rad（0.96°）、`r_elbow_y` 残差 0.0407 rad（2.33°） | 通过 |
| B | 未点名关节不被误动 | 8 个对照关节最大漂移 0.0238 rad（1.36°） | 通过 |
| C | 覆盖接管延迟 | ≈ **一个发布周期**（20 Hz → 0.05 s；5 Hz → 0.20 s） | 通过 |
| D | 释放后回归 | 完全回归 **0.4–0.5 s**（非 0.2 s，见 §3.2） | 通过 |

两条新增实测参数：

1. **覆盖通道与状态话题的 QoS 均为 `BEST_EFFORT`**，与 rclpy 默认的 `RELIABLE` 不匹配，
   订阅端会静默收不到任何消息。任何自写节点必须显式对齐 QoS（见 §3.1）。
2. **覆盖释放 = `timeout 0.2 s` + `release_blend 0.2 s` 两段**。官方仅记载 `timeout=0.2 s`；
   实测停发后 0.2 s 时刻关节仍保持原位不动，随后在约 0.2 s 内混合回策略输出（见 §3.2）。

v1.1 追加的实测结论（含一条负面结果）：

| 项 | 结论 | 位置 |
|---|---|---|
| 相机方位角 | 机器人朝 **+x**，身体右侧为 **−y**；录右臂必须用方位角 **270–330°**，用 90° 会拍到左臂且右臂被躯干完全遮挡 | §4 |
| 官方控制器增益 | 31 个关节的 `kp`/`kd` 已实测成表，自写覆盖节点应沿用 | §5 |

## 1. 验证方法

不使用屏幕目视比对。判据全部由 `/simulation/actuator_states` 的关节角度读数给出硬证据。

探针流程：

1. 订阅 `/simulation/actuator_states`，取 31 关节位置的基线；
2. 仅向 `/simulation/actuators_cmds_override` 发布**右臂 7 个关节** =
   `实测基线 + 增量`（`r_shoulder_y_joint` 加 +0.20 rad、`r_elbow_y_joint` 减 0.20 rad），
   其余 24 关节一概不发；
3. 持续发布若干秒，记录关节实际位置；
4. 停止发布，以 0.05 s 分辨率记录回归过程。

> 目标值取自**实测基线 + 增量**，而非凭空填写，因此本次验证只用于证明通道可用，
> 不构成任何可用于真机的抓取位姿。抓取位姿仍须按 `docs/13` §4.3 用官方 IK 求解后填入
> `config/arm_poses.yaml`。

`kp` / `kd` 取 `config/arm_poses.yaml` 中的 `default_kp` / `default_kd`（官方 B 组，较柔和）。

### 2.1 判据 A —— 点名关节跟到目标

| 关节 | 基线 | 目标 | 持握末实测 | 残差 |
|---|---|---|---|---|
| `r_shoulder_y_joint` | +0.18305 | +0.38305 | +0.36622 | 0.01683 rad（0.96°） |
| `r_shoulder_x_joint` | −0.19828 | −0.19828 | −0.17330 | 0.02499 |
| `r_shoulder_z_joint` | +0.03245 | +0.03245 | +0.05618 | 0.02373 |
| `r_elbow_y_joint` | +0.61607 | +0.41607 | +0.45671 | 0.04065 rad（2.33°） |
| `r_wrist_x_joint` | −0.00328 | −0.00328 | −0.00346 | 0.00017 |
| `r_wrist_y_joint` | −0.00348 | −0.00348 | −0.00197 | 0.00151 |
| `r_wrist_z_joint` | +0.00592 | +0.00592 | +0.00616 | 0.00025 |

两个施加增量的关节均明显跟随（移动幅度 0.18 / 0.16 rad）。

**残差说明**：稳态残差来自仿真侧驱动为纯 PD、无重力补偿。
MuJoCo 独立仿真侧亦观察到同一现象（`docs/14` §9），非本次通道问题。

### 2.2 判据 B —— 未点名关节不被误动

对照组 8 个关节（腰 2、左臂 3、右腿 2、头 1）：

| 关节 | 基线 | 持握末 | 漂移 |
|---|---|---|---|
| `waist_y_joint` | +0.01564 | +0.00447 | 0.01118 |
| `waist_x_joint` | +0.00019 | +0.00208 | 0.00189 |
| `l_shoulder_y_joint` | +0.18232 | +0.16061 | 0.02171 |
| `l_shoulder_x_joint` | +0.19903 | +0.19281 | 0.00623 |
| `l_elbow_y_joint` | +0.61584 | +0.63934 | 0.02350 |
| `r_hip_y_joint` | −0.31670 | −0.31816 | 0.00145 |
| `r_knee_y_joint` | +0.60461 | +0.60541 | 0.00080 |
| `head_z_joint` | −0.00003 | +0.00001 | 0.00004 |

最大漂移 **0.0238 rad（1.36°）**，出现在 `l_elbow_y_joint`。

该量级小于姿态切换引起的平衡策略调整幅度，判定为策略对重心变化的正常响应，
而非覆盖作用到未点名关节 —— 覆盖的**关节选择是精确的**。

### 2.3 判据 C —— 接管延迟

在 6–20 Hz 区间，从第 1 条消息发出到关节开始移动的间隔**与发布周期一致**：

| 发布频率 | 实测接管延迟 | 1 / 频率 |
|---|---|---|
| 20 Hz | 0.05 s | 0.050 s |
| 10 Hz | 0.10 s | 0.100 s |
| 5 Hz | 0.20 s | 0.200 s |
| 4 Hz | 0.25 s | 0.250 s |

→ 测量分辨率即发布周期，可判定**接管无额外延迟**：消息到达即生效。
编排动作时按一个周期量级预留即可，不需要为「接管耗时」单独留余量。

### 2.4 判据 D —— 释放与回归

停发后以 0.05 s 分辨率采样（增量 0.20 rad）：

| 停发后时刻 | `r_shoulder_y` | `r_elbow_y` | 相对基线残差 |
|---|---|---|---|
| 0.00 s | +0.36553 | +0.45638 | 0.18331 |
| 0.15 s | +0.36553 | +0.45638 | 0.18331 |
| **0.20 s** | +0.36333 | +0.45989 | 0.18111 |
| 0.25 s | +0.34778 | +0.48105 | 0.16556 |
| 0.30 s | +0.31983 | +0.51103 | 0.13761 |
| 0.40 s | +0.23983 | +0.57831 | 0.05761 |
| **0.50 s** | +0.18671 | +0.60240 | 0.01329 |
| 1.00 s | +0.17848 | +0.61621 | 0.00374 |
| 2.00 s | +0.18017 | +0.61540 | 0.00205 |

**0.2 s 时刻残差仍为 0.18111 rad，几乎等于增量本身** —— 即此时关节**一点没动**。
真正开始回归发生在 0.2 s 之后，在 0.5 s 时残差降至 0.0133 rad。

该现象由框架启动日志直接印证：

```
motor override input: topic=simulation/actuators_cmds_override,
                      timeout=0.200s, release_blend=0.200s
```

→ 释放过程是**两段**：`timeout` 0.2 s（保持最后一帧指令）+ `release_blend` 0.2 s（混合回策略）。
详见 §3.2。

## 3. 新增实测参数

### 3.1 ★ 覆盖通道与状态话题的 QoS 均为 `BEST_EFFORT`

`ros2 topic info -v` 实测：

| 话题 | Reliability | Durability |
|---|---|---|
| `/simulation/actuator_states`（仿真 → 控制器） | `BEST_EFFORT` | `VOLATILE` |
| `/simulation/actuators_cmds_override`（订阅端） | `BEST_EFFORT` | `VOLATILE` |

`rclpy` 的 `create_subscription` / `create_publisher` **默认是 `RELIABLE`**。
不显式对齐时，订阅端表现为：

```
[WARN] New publisher discovered on topic '/simulation/actuator_states',
       offering incompatible QoS. No messages will be received from it.
       Last incompatible policy: RELIABILITY
```

**症状极具误导性**：节点正常启动、`ros2 topic list` 能看到话题、
`ros2 topic echo` 能正常打印消息（`ros2 cli` 会自动适配 QoS），
唯独自写节点**一条也收不到**，且不抛异常。

处理方式（`tools/m0_override_check.py` 已内置）：

```python
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy, DurabilityPolicy

QOS_BE = QoSProfile(
    reliability=ReliabilityPolicy.BEST_EFFORT,
    history=HistoryPolicy.KEEP_LAST,
    depth=10,
    durability=DurabilityPolicy.VOLATILE,
)
node.create_subscription(ActuatorStates, TOPIC, cb, QOS_BE)
```

> 排查提示：自写 ROS 2 节点「话题看得见、echo 有数据、但回调不进」时，
> **第一件事查 QoS**，不要怀疑话题名或 domain。
>
> 补充：命令行侧同样受此影响。`ros2 topic echo --once <话题>` 在未加
> `--qos-reliability best_effort` 时输出为空且退出码为 0，不会报错。

### 3.2 ★ 覆盖释放为两段：`timeout` + `release_blend`

官方 `docs/13` §1.1 记载「覆盖超时 0.2 s」，未提及混合段。实测框架参数为：

```
timeout=0.200s        最后一帧指令的保持时长
release_blend=0.200s  之后混合回策略输出的时长
```

时间线（数值见 §2.4）：

```
发布停止
   │
   ├─ 0.00 ~ 0.20 s   指令保持，关节纹丝不动          ← timeout
   ├─ 0.20 ~ 0.40 s   平滑混合回策略（约 0.5 s 处基本归位） ← release_blend
   └─ 0.50 s 以后     完全由策略接管
```

**对动作编排的意义**：若在动作之间插入了「停止发布」的间隔，
必须按 **0.4 s** 而非 0.2 s 估计机器人手臂的实际回落时间；
若这段时间内手正抓着物体，物体在这 0.4 s 内处于「指令渐失」状态。

### 3.3 发布频率边界

固定增量 0.20 rad、持续 6–8 s，扫描发布频率。指标为
「接管成功之后 0.5 s 起统计的持握段最大残差」：

| 发布频率 | 接管延迟 | 持握段最大残差 | 判定 |
|---|---|---|---|
| 20 Hz | 0.05 s | 0.0415 rad（2.38°） | 稳定 |
| 10 Hz | 0.10 s | 0.0415 rad（2.38°） | 稳定 |
| 9 Hz | 0.11 s | 0.0414 rad（2.37°） | 稳定 |
| 8 Hz | 0.13 s | 0.0417 rad（2.39°） | 稳定 |
| 7 Hz | 0.14 s | 0.0414 rad（2.37°） | 稳定 |
| 6 Hz | 0.17 s | 0.0417 rad（2.39°） | 稳定 |
| **5 Hz** | 0.20 s | 0.0415 rad（2.38°） | **稳定（临界点）** |
| 4 Hz | 0.25 s | 0.0441 rad（2.53°） | 开始回混（约 25%） |
| 3 Hz | 0.33 s | 0.0826 rad（4.73°） | 回混（约 41%） |
| 2 Hz | 2.50 s | 0.1727 rad（9.89°） | 回混约 86%（≈ 全掉），判据 A 不通过 |

结论：

1. **官方「必须 ≥ 5 Hz」的要求成立且是临界值**。5 Hz 时下一条消息恰好落在
   `timeout` 到期瞬间，来不及进入 `release_blend`，因此仍稳定。
2. 低于 5 Hz 后出现**周期性回混**：每两条消息之间的空档超过 0.2 s，
   框架已在用 `release_blend` 把关节往回混合，下一条消息到达后再拉回，形成锯齿。
3. 净稳态误差 0.0415 rad（2.38°）在 5 Hz 以上不随频率变化，来源为 PD 静差，非覆盖缺口。
4. 回混比例可用 `(1/频率 − 0.2) / 0.2` 估算。实测比线性预测偏小
   （3 Hz 线性预测 67%、实测 41%），说明 `release_blend` 曲线带缓入。

> **实践取值建议**：按 20 Hz 发布（`config/arm_poses.yaml` 的 `min_publish_rate_hz` 目前写 5，
> 属理论下限）。低于 10 Hz 后虽然仍能维持，但已无裕量，任何一次调度抖动都会啃掉安全边距。
>
> **统计口径提醒**：判定「有没有掉覆盖」时，统计窗口必须以**接管成功时刻**为起点。
> 低频率下接管本身就要一个发布周期（4 Hz 时 0.25 s），若从固定时刻起算，会把
> 「还没接管」读成「覆盖掉了」，从而得出完全相反的结论。本次实测中该错误一度
> 导致「6 Hz 就掉覆盖」的误判，修正口径后数据完全不同（4 Hz 亦稳定）。

## 4. ★ 机器人朝向与相机方位角

这一节是 v1.1 新增。**录不出「手臂在动」的画面，最常见的原因不是动作太小，而是机位拍错了侧。**

### 4.1 坐标系事实

由模型与实测共同确定：

| 项 | 值 | 来源 |
|---|---|---|
| 机器人朝向 | **+x** | 正面影像在方位角 0° 取得 |
| 静止时右腕位置 | (+0.256, **−0.178**, +0.931) m | `r_wrist_z_link` 的 `data.xpos`，MuJoCo 世界系 |
| 因此「身体右侧」方向 | **−y** | 右手腕的 y 小于躯干 |

### 4.2 方位角语义与右臂可见性

MuJoCo 自由相机的 `azimuth` 是相机在世界 xy 平面上的方位。对照上表：

| azimuth | 相机位置 | 看到的部位 | 右臂（被驱动的那条） |
|---|---|---|---|
| 0° | +x 侧 | **正面** | 可见，在画面左侧 |
| 90° | **+y 侧** | 机器人**左侧** | ❌ **被躯干完全遮挡** |
| 180° | −x 侧 | 背面 | 可见，在画面右侧 |
| 270° | **−y 侧** | 机器人**右侧** | 可见，离相机最近 |
| **315°** | +x, −y 之间 | **右前三刻钟** | ✅ **可见且轮廓最清楚** |

### 4.3 实测后果

同一段右臂轨迹，仅改机位：

| 机位 | 观感 |
|---|---|
| `azimuth 90`、距离 4.2 m | 手臂与躯干、大腿轮廓重叠（白叠白），**目视几乎看不出在动** |
| `azimuth 312`、距离 3.0 m，另加特写机位 | 手臂从垂直到前伸、外展的全程**一眼可辨** |

本仓库成品采用 **azimuth 312° / 距离 3.0 m / 俯仰 −8°**，特写机位
**距离 1.75 m、视线偏移 `(0, −0.14, −0.10)`**。

### 4.4 机位选择不必靠试错

`tools/pose_cam_grid.py` 可以**离线**把机器人摆成若干姿态、用若干机位各渲一张拼成网格，
用来客观挑选机位，同时打印各关节的模型真实限位。该脚本不订阅话题、不发布指令、
不修改官方 XML，跑一次只需要几秒。

```bash
MUJOCO_GL=egl python3 tools/pose_cam_grid.py \
    --model <官方 elf3.xml> --out grid.png \
    --poses rest,reach_a,reach_c --azimuths 0,90,270,315 --distance 2.9
```

### 6.1 修正一条先前的判断

`docs/14` 曾记录「右臂大幅侧展只能靠 `shoulder_z`」。该判断不成立 ——

`r_shoulder_x_joint` 负向有 **175°** 行程，正是右臂外展方向。实测单关节转 51.6°
（约 0.90 rad）的末端位移：

| 关节（单项 51.6°） | 腕位移 | Δx | Δy | Δz | 动作性质 |
|---|---|---|---|---|---|
| `r_shoulder_x_joint` −51.6° | 222.7 mm | 0 | **−201** | **+97** | **抬臂外展**（向外 + 向上） |
| `r_shoulder_z_joint` +51.6° | 222.7 mm | −97 | **+201** | 0 | 水平横扫（跨过身体中线） |
| `r_shoulder_z_joint` −51.6° | 222.7 mm | −97 | **−201** | 0 | 水平横扫（向外） |

→ 需要「**抬起来**」用 `shoulder_x` 负向；需要「**横着扫**」用 `shoulder_z`。
两者位移模长相同但方向不同，`shoulder_z` 的 Δz 恒为 0。

## 7. ★ 大幅动作对机体的扰动：走动阈值

覆盖右臂时，**平衡控制器会把手臂动作当作重心扰动，并用迈步来吸收**，
结果是机体在仿真世界里被带走数米。

指标定义（两个口径必须分开，见 §9）：

- **① 手臂动作** = 右腕相对躯体的位移
- **② 机体走动** = 躯体在世界系里的位移（取 `/simulation/odom` 真值）

扫描条件：`tools/arm_wave_demo.py --scale S`，同一条 16.5 s 轨迹，观察 20 s。

| 幅度 scale | ① 手臂动作 | ② 机体走动 | 观感 |
|---|---|---|---|
| **0（不发任何指令，空跑对照）** | 0.1 mm | **0.000 m** | 机器人 20 s 内一步不走 |
| 0.35 | 32.3 mm | 0.121 m | 镜头基本不动 |
| 0.55 | 89.8 mm | 0.471 m | 镜头轻微跟动，背景开始变 |
| **1.00** | **199.8 mm** | **4.096 m** | 镜头跟着跑，背景完全改变 |

结论：

1. **空跑对照为 0.000 m**，故机体走动确定由手臂覆盖动作诱发，不是仿真自身的漂移。
2. 关系**强超线性**：幅度从 0.55 升到 1.00（×1.82），走动从 0.471 m 升到 4.096 m（×8.7）。
   即存在一个阈值区间，跨过之后控制器由「倾身吸收」切换为「迈步」。
3. 该现象对真机有直接含义：**大幅手臂动作会扰动平衡**，
   `docs/13` §5 安全红线第 1 条（落地承重前必须先进入 `hello` / `applause` 等
   不依赖手臂维持平衡的状态）在此获得仿真侧的支持。
4. 做「只看手臂」的演示时，不要试图用覆盖通道锁住下肢（见 §8），
   应改为在**渲染侧**钉住基座（见 §10）。

## 8. ★ 失败记录：锁定下肢会让机器人摔倒

**动机**：既然 §7 的走动来自平衡控制器迈步，直觉做法是把下肢关节也一起覆盖、锁在基线站姿，
让机体无法迈步，画面就只剩手臂动作。

**做法**：`tools/arm_wave_demo.py --hold-legs` —— 覆盖扩展为
右臂 7 + 腰 3 + 腿 12 = 22 个关节，下肢目标取基线值，增益沿用 §5 的官方实测值。

**结果**：**失败，且是反向效果**。

| 指标 | 实测 |
|---|---|
| 基座 z 变化 | 由 ≈1.03 m 降至 ≈0.09 m，**掉落 0.944 m** |
| 摔倒时刻 | 覆盖开始后约 3–4 s |
| 结束时右腕相对躯体位移 | 531.5 mm（手臂未回到静止位，随机体倒下而乱置） |

**机理**：踝关节被锁死后，平衡控制器同时失去两种手段 ——
踝策略（踝关节主动出力调节压力中心）与迈步策略（通过落脚点改变支撑多边形）。
两者皆无时，即使很小的重心偏移也无法恢复，机体必然倾倒。
即：**控制器的迈步不是缺陷，而是它维持站立的手段。**

**保留在代码里的原因**：该选项标注为「实测无效，勿用」，避免重复踩坑。
要得到「机体不动、只有手臂动」的画面，正确做法是在**渲染侧**处理（§10），
不改变仿真本身的任何状态。

## 9. ★ 位移口径铁律：两个位移必须分开报

首版观察者脚本只报「右腕在世界系里的位移」，得到 **3940 mm** 的荒谬读数 ——
机器人才 1.45 m 高，手腕不可能移动 3.9 m。

原因：机体本身在该次录制中走了 4.04 m（§7），
世界系里的腕位移把「机器人走路」和「手臂行程」加在了一起。

修正后分两个口径输出：

| 口径 | 定义 | 含义 |
|---|---|---|
| **① 手臂动作** | `xpos[腕] − xpos[躯体]` | 手臂本身的行程，与机体是否移动无关 |
| **② 机体走动** | `/simulation/odom` 位置相对首帧的位移 | 平衡控制器有没有迈步把机体带走 |

同一段轨迹的两个口径对比（幅度 ×1.0）：

| 口径 | 实测 |
|---|---|
| ① 手臂动作 | **199.8 mm**（Δx −102.0 / Δy −155.9 / Δz +72.1），末帧 6.6 mm（已回位） |
| ② 机体走动 | **4.110 m**（终点 −2.676, −3.044, +0.004） |

> 通用教训：**任何「某部件相对某参考」的运动量，都必须明确写出参考系。**
> 参考系取世界系时，机体自身的运动会被混入。

## 10. 无显示器环境下的出图方案：远程观察者

### 10.1 为什么不能用现成的相机

`172.16.10.133` 只能 SSH 访问，机上 MuJoCo GUI 窗口用的是自由相机，
默认朝向远处的城市地形而**不在机器人身上**；仿真内建的两个相机
（胸口 `body_depth_camera`、头部 `head_depth_camera`）都装在机器人身上，**拍不到自己**；
而仿真节点只暴露 `simulation/model_file` 一个参数，相机无法从 ROS 侧调整。

### 10.2 做法

绕开 GUI 与内建相机：`tools/ros2_mujoco_spectator.py` 订阅机器人状态，
写回**同一份官方模型**的 `qpos`，用自定义相机离线渲染，直接输出 MP4。

```bash
MUJOCO_GL=egl python3 tools/ros2_mujoco_spectator.py \
  --model ~/elf3_ws/bxi_rl_controller_ros2_example/src/bxi_example_py_elf3/data/mujoco_simulation/elf3.xml \
  --out shots/final2.mp4 --gif shots/final2.gif --gif-width 560 --gif-stride 3 \
  --seconds 21 --fps 30 \
  --cam-mode follow --azimuth 312 --distance 3.0 --elevation -8 --follow-z-offset -0.35 \
  --split --cam2-distance 1.75 --cam2-lookat-offset "0,-0.14,-0.10" \
  --skeleton --pin-base --freeze-lower \
  --label "FULL BODY" --label2 "ARM CLOSE-UP" \
  --width 640 --height 720
```

关键实现点：

| 项 | 做法 | 原因 |
|---|---|---|
| 离屏帧缓冲 | 构造 `Renderer` **之前**改内存里的 `model.vis.global_.offwidth/offheight` | 默认为 640×480，不改会直接报 `Image width 960 > framebuffer width 640`；改内存可避免动官方 XML |
| 视线中心 | 用 `data.xpos[root_body]` 模型真值，不用 odom | odom 原点与 MuJoCo 世界系存在常量偏移，侧视时机器人会偏出画面 |
| 双画面 | 同一次渲染循环里渲两个机位再 `hstack` | 时间严格同源；合帧后才叠 HUD，避免叠加层画两遍 |
| 骨架线 | `mjv_initGeom` + `mjv_connector` 往 `renderer.scene` 里追加胶囊与球 | 坐标取 `data.xpos` 真值，是可视化，不改动力学 |
| 中文叠加 | 一律用 ASCII | `cv2.putText` 的 Hershey 字体无 CJK 字形，中文会渲染成 `??????` |

### 10.3 两个渲染期开关

| 开关 | 作用 | 适用场景 |
|---|---|---|
| `--pin-base` | 基座（free joint）钉在录制起始位姿，镜头与背景固定 | 大幅动臂诱发机体走动（§7）时保持画面稳定 |
| `--freeze-lower` | 下肢（腰 3 + 腿 12）冻结在首帧站姿，只有右臂 7 个关节跟随 ROS | 避免机体走动带动腿部出现「原地踏步」的怪异站姿 |

两者都**只在渲染侧生效**，不改变仿真状态、不发任何指令。
开启时画面底部会自动叠加
`render note: base pinned + lower body held at t0 | arm joints are live ROS data`，
以便视频脱离上下文时仍能正确解读。

### 10.4 成品指标

| 项 | 值 |
|---|---|
| 视频 | `shots/final2.mp4`，630 帧 @ 30 fps，1280×720（双画面），7.2 MB |
| GIF | 210 帧 @ 100 ms，560 px 宽，11.5 MB |
| 渲染速度 | 8–10 ms/帧（双画面，EGL 离屏） |
| 指令跟随残差 | `sh_y` ≤ 2.9°，`sh_x` ≤ 6.5° |
| ① 手臂动作 | 199.8 mm |
| 画面证据 | 帧差（已排除 HUD 与底部角标）：特写面板变化像素 **7.98%**，包围盒 x[49..447] y[123..619]，**变化集中于手臂**，躯干/头/腿区域内无变化 |

## 11. 脚本坑：`set -u` 与 ROS `setup.bash`

shell 脚本里若在 `source` ROS 环境**之前**打开 `set -u`，会得到**零输出、退出码 1** 的静默失败：

```bash
$ bash -c 'set -u; source ~/elf3_env.sh; echo DONE'
/opt/ros/humble/setup.bash: 行 8: AMENT_TRACE_SETUP_FILES: 未绑定的变量
# DONE 永不打印，且没有任何更上层的提示
```

原因：`setup.bash` 第 8 行读取可能未定义的 `AMENT_TRACE_SETUP_FILES`，
在 `set -u` 下非交互 shell 会把它当作致命错误并终止整个 shell。

规避顺序（`tools/run_arm_demo.sh` 已按此写）：

```bash
set +u                       # 先关掉
source "$HOME/elf3_env.sh"   # 再 source
export ROS_DOMAIN_ID=42
set -u                       # 之后才打开
```

## 12. 对后续动作编排的影响

1. **M0 已完成，覆盖通道可放心使用**；`tools/arm_pose_pub.py` 的安全门禁与
   `docs/13` §4.1 的操作顺序均得到实测支持。
2. **「臂先到位、手再闭合」的时序不变**，但两条通路的失效特征不同，需分别处理：

   | | 臂（覆盖） | 手（CANFD） |
   |---|---|---|
   | 发一次是否保持 | 否，`timeout` 0.2 s | 是，自行保持 |
   | 释放耗时 | 0.4 s（两段） | 无（发一次即维持） |
   | 安全发布频率 | ≥ 5 Hz（建议 20 Hz） | 不适用 |

3. **`release_blend` 的 0.2 s 混合段意味着「松手」不是瞬时事件。**
   若要在抓着物体时释放覆盖，物体将在约 0.4 s 内经历一次渐变的姿态回落。
4. `docs/13` §5 安全红线第 1 条（落地承重时必须先进入 `hello` / `applause`）依然适用，
   本次验证为纯仿真，未触发该条；§7 的走动实测为该条提供了仿真侧支持。
5. **编排幅度需与平衡能力联合考虑**。若某段动作会让机体明显移位，
   要么降低幅度（建议单关节 ≤0.3 rad 量级起步），
   要么在动作前切到不依赖手臂维持平衡的状态。
6. **覆盖节点的角度表必须带限位钳位**。覆盖通道本身不做限位检查，
   超限值会被直接下发；`tools/arm_wave_demo.py` 的做法是内置 §6 的实测限位表，
   发布前逐关节钳位并计数告警。
