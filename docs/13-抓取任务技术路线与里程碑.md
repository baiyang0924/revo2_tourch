# 13 · 抓取任务技术路线与里程碑

> **文档状态**：v1.1（2026-09-22）
> **目标动作**：伸手 → 抓起一瓶瓶装水 → 举起来
> **适用**：机器人已装好、Ubuntu 环境已按 `docs/12` 搭完
> **依据**：BXI 官方 Wiki 开发者文档（`arm_ik` / `mod_api_31dof_control` /
> `upper_body_teleop` / `dexterous_hand` / `manipulation`）+ 本仓库已有代码
>
> **侧别约定**：本项目 ELF3 实机装配的是**右手**（右腕 `r_wrist_z_link`，
> CAN6 / ID 127），本文命令与位姿均以右手/右臂为准。
> 左右手通路完全对称，切左手只需把 `--hand right` 换成 `--hand left`、
> `--sides right` 换成 `--sides left`（左手为 CAN5 / ID 126）。

## 0. 先直接回答你的三个问题

### 问题一：先编手部动作，还是先编机械臂动作？

**这是个伪二选一 —— 因为它俩是两条物理上完全独立的控制通路，可以并行推进。**

| | 手臂（本体 31 关节的一部分） | 灵巧手（6 个关节） |
|---|---|---|
| 走什么接口 | 话题 `/hardware/actuators_cmds_override` | CANFD，主控板 CAN5 / CAN6 |
| 消息 / SDK | `communication/msg/ActuatorCmds` | `bc-stark-sdk==1.5.1` |
| 怎么寻址 | **按关节名**（`r_elbow_y_joint`） | 按总线 + ID（右手 CAN6/127，左手 CAN5/126） |
| 命令多久失效 | **0.2 s 超时**，必须 ≥5 Hz 持续发 | 手自己保持，发一次就行 |
| 调它会不会影响另一条 | 不会 | 不会 |

所以「先搞哪个」这个问题本身没有抢占关系。**真正有先后的是执行时序**：

```
伸手 ──────► 到位 ──────► 停住 ──────► 手闭合 ──────► 抬起来
（臂）        （臂）        （臂）        （手）          （臂 + 手保持）
```

**臂必须先到位，手才能闭合。** 顺序反了就是手在空中乱抓 —— 抓不到东西，
而且如果是真机，手还可能抓到自己的线缆或衣服。

**结论**：两条线并行做，但任何一次「抓」的动作编排，都必须是臂在手前面。

### 问题二：这种是不是得靠视觉识别 + 自主算法？是不是很难？

**你的判断是对的：最终形态一定是那个。但「现在就开始做」会卡死。**

三条硬理由：

1. **官方这条路的文档是空的。** 我查了 BXI Wiki 的开发者文档目录，`manipulation.zh.md`
   打开只有四行小标题（`pipeline简介` / `理论指引` / `训练环境` / `部署框架`），
   **正文一个字都没有**。对比 `arm_ik`、`dexterous_hand`、`upper_body_teleop`
   那几篇都是完整可照抄的 —— 说明视觉抓取这条线厂商还没放出公开方案。
2. **它是整条链上最长的一段。** 光前置条件就有：深度相机标定 → 手眼标定
   （相机坐标系 ↔ 腕部坐标系）→ 目标检测/位姿估计 → 抓取位姿生成 → IK →
   轨迹规划 → 碰撞检查。**每一环都是几周量级**，而且互相耦合（标定错了，
   后面所有环节的现象都是「抓偏了」，很难定位）。
3. **你手上没有必须现在做它的理由。** 融资 demo 要的是「机器人拿起一瓶水」这个
   **可见结果**，不是「用什么方法拿的」。示教 + 固定位置一样能演。

### 问题三：那快速见效的做法是什么？

**把「找瓶子在哪」这一步，用「人摆好」替代掉。**

```
难的路（先别走）:  相机找瓶子 → 算抓取位姿 → IK → 轨迹 → 抓
                       ▲▲▲▲▲▲▲▲ 这一段是几周的工作量
快见效的路:        人把瓶子放到标记位置 → 臂到位 → 手闭合 → 抬起来
                      ▲▲▲▲▲▲▲▲▲▲▲▲▲▲ 这一段 1~2 周就能出成果
```

第一阶段的目标不是「智能」，是「**通**」—— 证明臂和手能在同一时刻协同到位。
通了之后再往里加触觉、加视觉，每加一层都是增量，不是推倒重来。

## 1. 两条通路的技术细节（干活前先记住这几条）

### 1.1 手臂：按关节名覆盖

官方支持不写代码、直接发话题覆盖本体关节（文档：《最简控制 ELF3 的 31 自由度》）。

| 环境 | 话题 |
|---|---|
| 仿真 | `/simulation/actuators_cmds_override` |
| 真机 | `/hardware/actuators_cmds_override` |

消息是 `communication/msg/ActuatorCmds`，四个数组长度必须一致，
`actuators_name` 决定其余数组的**对应顺序**：

```
actuators_name: ["r_shoulder_y_joint", ..., "r_wrist_z_joint"]
pos:           [0.10, ...]        # 弧度
kp:            [54.224, ...]
kd:            [3.452, ...]
```

> ⚠️ **覆盖超时 0.2 s。** 这不是「建议 20 Hz」，是**硬要求**：
> 停止发布 0.2 秒后，框架就把这些关节混合回当前策略输出。
> 手臂正抓着瓶子的时候掉覆盖 = 瓶子被甩出去。所以必须持续发，不能 `--once`。

> ⚠️ **按钮事件是上升沿检测。** 手工发 `{btn_4: 1}` 之后**必须再发一次 `{btn_4: 0}`**，
> 否则下一次同一个按钮槽位不会产生新的上升沿 —— 表现是「第一次好使，之后没反应」。

双臂 7 关节名（官方 31 关节布局下标 15–21 / 22–28，本项目用右臂）：

```
右: r_shoulder_y  r_shoulder_x  r_shoulder_z  r_elbow_y  r_wrist_x  r_wrist_y  r_wrist_z
左: l_shoulder_y  l_shoulder_x  l_shoulder_z  l_elbow_y  l_wrist_x  l_wrist_y  l_wrist_z
```

### 1.2 灵巧手：走 CANFD，另一条路

官方《外接灵巧手》给的就是本项目的配置：

```python
right_ctx = await init_bxipci_device(6, 127, master_id=1, is_canfd=True, ...)  # 右手 CAN6
left_ctx  = await init_bxipci_device(5, 126, master_id=1, is_canfd=True, ...)  # 左手 CAN5（备选）
```

> 本项目装配的是**右手**，日常只用第一行。左右两行都列出来是为了对照：
> 两侧除了 (总线号, 设备ID) 不同，其余参数完全一致。

手通过 `/canfd_packet/rx` `/canfd_packet/tx` 与硬件节点通信，
**不经过 `actuators_cmds_override`**（那 31 个关节里不含手指）。

官方示例里手内置的动作序列有 `Open`、`Fist`、`Pinch`、`Point` 等 ——
下节会讲为什么**抓瓶子不能直接用 `Pinch`**。

### 1.3 一句话记住两边的差异

> **手是「发一次就保持」，臂是「不发就失效」。**

这条差异是你第一次编排协同动作时会踩的坑：
写循环的时候如果两只手用同一套发一帧就 sleep 的逻辑，
手会一直抓着，臂会在 0.2 s 后自己回去。

## 2. 任务本身的难度：抓一瓶水要解决什么

### 2.1 物理参数（按常见 500 ml 瓶估算，实测为准）

| 项目 | 近似值 | 对抓取的影响 |
|---|---|---|
| 瓶身直径 | 约 6.3–6.7 cm | 决定四指张开行程 |
| 整瓶高度 | 约 21 cm | 决定抓握高度范围 |
| 满水重量 | 约 0.5 kg | 决定需要的保持力 |
| 表面 | 光滑柱面、可能有冷凝水 | **摩擦系数低，是最麻烦的一点** |

### 2.2 抓握方式：对掌包络抓，不是捏

| 方式 | 英文 | 适用 | 抓水瓶 |
|---|---|---|---|
| 对掌包络抓 | power grasp | 圆柱、大而重 | ✅ **用这个** |
| 指尖捏 | pinch | 小、轻、薄 | ❌ 光滑瓶身会滑 |
| 侧捏 | lateral | 卡片、钥匙 | ❌ |

要点：

- 拇指**外展对掌**，与四指形成包络，不是五根指头并排去夹；
- 抓握高度取**瓶身中下部**：重心低、且避开水瓶肩部那段收窄的曲线；
- 靠「**包住 + 预紧力**」而不是「夹住」—— 夹的接触面小，稍微一晃就滑。

### 2.3 三个真实难点（按遇到的顺序）

1. **手型不对 → 抓不住或捏飞。** 角度不够就包不住，过头就把瓶子挤出去。
   这个只能在桌上空抓 + 真机上反复试，**没法靠算**。
2. **时序不对 → 手在瓶子上方就闭合了。** 臂没到位、或臂超时缩回去了。
3. **抬起后滑脱。** 抓的瞬间够紧，抬起来一动就滑 —— 因为接触点受力变了。
   这一条要靠阶段 M4 的触觉/电流反馈解决，先有个预期。

### 2.4 强烈建议：先把难度降下来

练的时候**别一上来就用满瓶水**：

```
✅ 第 1 天：空瓶（最轻，掉了不心疼）
✅ 第 2 天：装 1/3 水
✅ 之后：   满瓶
```

更保险的第一步其实是用**泡沫圆柱 / 卷起来的纸筒**代替瓶子 —— 轻、软、不怕摔，
先把手型和时序跑顺，再换成真瓶子。

## 3. 六阶段路线图

每个阶段都有**明确的可验收成果**，做完一个再进下一个。

| 阶段 | 做什么 | 看得见的成果 | 风险 | 依赖硬件 |
|---|---|---|---|---|
| **M0** | 仿真里用话题覆盖手臂关节 | 屏幕上手臂抬起来了 | 零 | 不用 |
| **M1** | 定「抓瓶手型」并验证 | 手在空气中摆出能包住瓶子的形状 | 零 | 手（桌面/整机都行） |
| **M2** | 真机上让手臂到你指定的角度 | 真机手臂到达指定姿态且稳 | 中 | 机器人 |
| **M3** | **固定位置抓取** | **一键：臂到位 → 手闭合 → 抬起，水瓶离地** | 中高 | 机器人 + 手 |
| **M4** | 触觉/电流判「抓稳了」 | 轻轻推瓶子，手会自动补力不松 | 中 | 同上 |
| **M5** | 加相机找瓶子 | 瓶子挪 10 cm 照样抓得住 | 高 | + 相机 |
| **M6** | 自主算法（学习类） | 任意物体、任意位置 | 很高 | + 算力 |

**M3 就是你的第一个真成果**，也是能拿去演示的那一版。M4 之后是「更稳」，
M5 之后才是「更智能」。**不要跳到 M5。**

## 4. 各阶段怎么做

### 4.1 M0 —— 仿真里先让手臂动起来（零风险，先做这个）

为什么要先在仿真做：真机上覆盖手臂关节会**和平衡策略打架**（见 §5），
仿真里没有这个风险，可以放心把角度调大、试到你觉得顺手为止。

```bash
# 终端 1：仿真器
source ~/elf3_env.sh
ros2 launch bxi_example_py_elf3 example_launch_demo.py

# 终端 2：先零位模式
ros2 topic pub --once /motion_commands communication/msg/MotionCommands "{btn_4: 1}"
ros2 topic pub --once /motion_commands communication/msg/MotionCommands "{btn_4: 0}"

# 终端 3：覆盖右臂（用本仓库工具，位姿从 config/arm_poses.yaml 取）
python3 tools/arm_pose_pub.py zero --check-only     # 先看安全检查
python3 tools/arm_pose_pub.py zero --dry-run        # 再看会发什么
python3 tools/arm_pose_pub.py zero --sides right --rate 20 --seconds 5
```

`tools/arm_pose_pub.py` 是本次新增的工具，它把角度和关节名存在
`config/arm_poses.yaml` 里按名字取，避免手抄数组时错位（错位不报错，只是别的关节在动）。

> ⚠️ **仿真和真机的态度要反过来**：仿真里大胆试，真机上保守试。
> 工具默认只发仿真话题，发真机必须显式加 `--topic-prefix hardware --i-know-its-real`。

**验收**：仿真窗口里手臂明显抬起来了，且松手（停止发布）后手臂自己回到原姿态
—— 后者说明你正确理解了「0.2 s 超时」。

### 4.2 M1 —— 定「抓瓶手型」

**这一步不需要机器人**，手在桌面上就能做（就是你在 Windows 上已经会的那套）。
目标是把「包住直径 6.5 cm 圆柱」这个手型定下来。

**起点不用从零开始**：`config/gestures.yaml` 里已经有 `cylinder_grasp`
（圆柱握，备注就写着「抓水杯、瓶子」）：

```yaml
cylinder_grasp:
  description: 圆柱握（抓水杯、瓶子）
  angles: [45, 60, 60, 60, 60, 60]   # ⚠️ 示例值，需要按手感调
  duration_ms: 1200
  note: 拇指 Aux 需要电流维持锁定（拇指无机械锁定）
```

把它当**起点**，在真机上按下面的顺序调，然后把调好的值另存成 `bottle_grasp`，
**不要直接改 `cylinder_grasp`**（那个可能还有别的用途）。

```
顺序固定: [拇指Flex, 拇指Aux, 食指, 中指, 无名指, 小拇指]
上限:      59        90        81    81    81      81   （度）
```

调的顺序（**别跳第 1 步**）：

1. 单指、2° 幅度 → 确认「数值变大 = 弯曲还是张开」；
2. 每次加 10° 左右，逐指放开行程；
3. 手上拿一个空瓶，看**四指内表面是否都贴到瓶身**（触觉版可以直接看触觉读数判断）；
4. 重点感受**拇指 Aux**：它负责把拇指摆到对掌位置，是能否「包住」的关键。
   官方备注点明了**拇指没有机械锁定**，需要电流持续维持 —— 所以抓握期间
   这条通路的指令不能断（好消息是手发一次就保持，不会像臂那样 0.2 s 超时）；
5. 记下最终值。**这里是「度」，代码和寄存器用「度」，
   而上位机界面滑块是 0–100 百分比** —— 这两个绝不能混（见 `docs/07`）。

> ⚠️ 试的时候手上托着，别让瓶子掉到地上 —— 摔碎的玻璃瓶就别拿来试。

**验收**：空瓶放在手心里，手闭合后瓶子不会掉，也**没有把瓶子捏变形/挤出去**。

### 4.3 算手臂位姿：官方 IK 脚本

M2 需要「手应该伸到哪里」变成「7 个关节角」。官方给了 Pinocchio 的阻尼最小二乘脚本。

```bash
mkdir -p ~/elf3_arm_ik && cd ~/elf3_arm_ik
# 从 BXI_Wiki 的 assets 目录下载：
#   elf3_arm_l.urdf  elf3_arm_r.urdf  pinocchio_ik_solve.py  pinocchio_ik_solve_r.py
#   本项目用右臂 → 用 elf3_arm_r.urdf + pinocchio_ik_solve_r.py
python3 -m venv .venv && source .venv/bin/activate
pip install --upgrade pip
pip install pin scipy          # ★ 包名是 pin，不是 pinocchio
python -c "import pinocchio as pin; print(pin.__version__)"   # 官方用 pin 4.1.0 验证
python pinocchio_ik_solve_r.py
```

**三个必须知道的坑：**

1. **官方示例脚本自带的那个目标位姿没有收敛。** 官方原文：
   跑完 1000 次迭代后误差范数约 `0.1787`（容差是 `1e-5`），
   肘关节顶到下限 `-0.95993`、腕部 Y 顶到上限 `1.309`。
   **官方明确写了「不应直接用于真机」。** 所以「打印出数组」不等于「解出来了」——
   你自己的目标位姿跑完后，**必须重新算一次误差并检查是否小于容差**。
2. **末端坐标系的原点不在掌心，也不在指尖。** 右臂是 `r_wrist_z_link`，
   原点位于腕部 X/Y/Z 三个转轴的交点。
   **所以「让手腕到瓶子正上方」和「让手掌到瓶子正上方」差了整整一个手掌的距离** ——
   见 §4.4。
3. **简化 URDF 的 `base_link` 在肩膀，不是躯干。** 官方原文：
   「计算结果若要用于完整机器人模型，必须先做坐标变换」。
   零位时末端原点相对该 `base_link` 位于 `(0.256, 0, -0.256) m`。

修改目标位姿的地方：

```python
target = pin.SE3(
    R.from_euler("xyz", [roll, pitch, yaw], degrees=True).as_matrix(),
    np.array([x, y, z]),      # 单位 m，简化 base_link 坐标系
)
```

> 7 自由度手臂对 6 维位姿是**冗余**的，同一个目标有多组解。
> 连续轨迹要把**上一帧的解作为下一帧的初值**，否则关节角会跳变。

### 4.4 腕部 → 手掌的偏移（这一条漏了就会一直抓偏）

IK 解出来的是**腕部原点**的位姿。要抓瓶子，你要的是**手掌抓握中心**落在瓶身上。
这两个点之间有一个固定的刚体变换：

```
r_wrist_z_link 原点 ──(固定偏移)──► 抓握中心（手掌中心/虎口位置）
```

做法：让手张开、掌心朝下，**用尺子量**腕部原点到掌心的距离（或者从手部 MJCF/URDF 里查），
然后把这个偏移加到 IK 的目标上。因为末端坐标轴在零位时与 `base_link` 平行
（官方说明），偏移可以直接在 `target.translation` 上做向量加减。

**如果你用的是「先手动摆出手型、看读数、再反推」的路子**，这个偏移其实已经被
手动试错吸收掉了 —— 这也是为什么 M1 手动试出来的手型配合手动试出来的位姿，
往往比纯算出来的更快能用。

### 4.5 M2 —— 真机上让手臂到位

⚠️ **先读 §5 的安全约束，尤其第 1 条。**

```bash
# 机器人上（真机程序需要 root）
sudo systemctl stop ros_elf_launch.service      # 先停自启动服务，避免两个程序同时控电机
sudo -i
source /opt/ros/humble/setup.bash
source /opt/bxi/bxi_ros2_pkg/setup.bash
source ~/bxi_ws/bxi_rl_controller_ros2_example/install/setup.bash
export ROS_DOMAIN_ID=<机器人的>

# ① 先进入不依赖手臂维持平衡的状态
ros2 topic pub --once /motion_commands communication/msg/MotionCommands "{btn_10: 7}"   # cheer
ros2 topic pub --once /motion_commands communication/msg/MotionCommands "{btn_10: 0}"   # 必须补 0！
#   或者用本仓库工具：./tools/elf3_cmd.sh cheer

# ② 用极小角度试方向（别直接用算出来的完整位姿）
python3 tools/arm_pose_pub.py zero --sides right --topic-prefix hardware \
    --i-know-its-real --rate 20 --seconds 5
```

**第一次必须比官方增益更小。** 官方两篇文档给的增益还不一致
（一组 `kp` 是 `[100, 80, 80, 100, 20, 20, 20]`，另一组是
`[54.224, 54.224, 16.747, 54.224, 16.747, 16.747, 16.747]`）——
本仓库台账默认取更柔和的那组，**第一次真机建议再乘 0.5**。
理由很直接：刚度低 = 撞到东西时更不容易硬顶。

**验收**：手臂到达目标角度、停得稳、松手后按预期回位。

### 4.6 M3 —— 固定位置抓取（第一个真成果）

把 M1 的手型和 M2 的臂位姿串起来，形成三个位姿 + 一个手型：

```
① pre_grasp   ：右手腕移到瓶子正上方约 10 cm，掌心朝下      ← 右臂
② grasp_close ：下到瓶身中下部，停住                          ← 右臂
③ 手闭合       ：执行 M1 定好的抓瓶手型                       ← 右手（发一次，自己保持）
④ lift        ：抬到展示高度                                  ← 右臂（保持抓握）
```

对应命令（本项目右手）：臂 `--sides right`、手 `--hand right`。

编排时记住 §1.3 那条差异：**臂要循环持续发，手只要发一次。**

瓶子位置用**标记贴纸**固定住 —— 贴一个角标，每次瓶子放同一个位置。
这就是「人摆好」替代「相机找」的具体做法。

**验收**：一条命令跑完，瓶子离地、手臂稳住 5 秒、再放回。

> 这一步做完，你就有能演示的东西了。之后再往 M4/M5 走都是增量。

## 5. 安全红线（照抄官方原文，不是我加的）

> ⚠️ **第 1 条是本次最重要的安全约束，不知道会摔机器人。**

1. **落地承重时覆盖手臂或手部关节，必须先进入不依赖手臂维持平衡的状态。**
   官方点名的两个：`com.bxi.basic_actions/hello`（挥手）、
   `com.bxi.basic_actions/applause`（鼓掌）。
   原因：`actuators_cmds_override` 只替换指定关节，
   **不能让原有平衡模型自动适应你的新手臂动作** —— 平衡策略正在用手臂配重，
   你把它抢过来，它就摔了。
2. **机器人吊装时**用 `actuators_cmds_override`，底层状态**只允许**
   `initial_pos`（零位）或 `pd_brake`；**禁止**进入走路、挥手、鼓掌、跳舞等任何其他模式。
3. **绝对不要在仿真开发机上运行带 `hw` 的 launch 文件** —— 那是驱动真实硬件的。
4. **失控保护 100 ms**：控制命令断流超过 100 ms → 电机失能，必须重新初始化。
   所以动作执行中不要切窗口、不要断 SSH。
5. **硬件保护计数器**：速度超限 +50、力矩超限 +100、正常消息 −1，
   **累计到 1000 电机退出使能**。频繁触发说明参数或姿态有问题，别靠重启硬扛。
6. **不要在真机上同时用两个程序控制同一台机器人 / 同一只手**（包括官方上位机和脚本）。
7. **新控制程序先在 MuJoCo 仿真验证，再上真机；异常时先按急停。**

> 有意思的一点：官方要求落地时先切到的 `hello` / `applause`，
> **正好是同事已经在 `mods/com.bxi.basic_actions` 里实现好的动作**。
> 也就是说这一条你不需要自己写代码，直接调现成的即可 —— 见 `README` 里那份同事成果索引。

## 6. 为什么先不做视觉（三条理由再强调一次）

| 理由 | 具体 |
|---|---|
| 没有官方方案 | `manipulation.zh.md` 只有标题没有正文，整条 pipeline 要自己搭 |
| 前置链条长且耦合 | 相机标定 → 手眼标定 → 位姿估计 → 抓取生成 → IK → 轨迹，任一环错都表现为「抓偏」 |
| 收益递减 | M3 已经能演示「拿起水瓶」；视觉只把「瓶子挪 5 cm 也能抓」变成可能 |

**唯一值得提前做的准备**：如果打算以后上视觉，**现在就把相机架好、标定数据留好**。
但别在 M3 之前碰它。
