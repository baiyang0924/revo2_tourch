# 环境边界与方案选型

> 本文回答一个被问了无数遍的问题：**Windows 能不能用 ROS 2 联动机器人来控制灵巧手？**
> 以及：如果不能，我们的方案该怎么定。

---

## 一、结论先给

**不能。但原因不是「Windows 装不了 ROS 2」——那句流行说法本身就是错的。**

正确的结论是：

> ROS 2 Humble **官方确实提供 Windows 10 的二进制安装包**，能在 Windows 上跑起来。
> 真正卡住我们的是**厂商链路**：精灵 3 的整机 SDK 和强脑的 ROS 驱动都只按 Ubuntu 构建与验证，
> 而且 CAN 总线在 Windows 上根本没有等价的系统级实现。
>
> **所以本项目采用：Windows 单独调手 + Ubuntu 22.04 双系统做 ROS 2 整机联调。**

答辩或被问到时，把下面 5 条原因说清楚，比重复「Windows 装不了」有说服力得多。

---

## 二、卡点逐条拆解（5 条）

### 1. 机器人机载主控本身就是 Ubuntu + ROS 2

精灵 3 的「大脑」（NUC）出厂跑的就是 **Ubuntu 22.04 + ROS 2 Humble**。
整机 SDK、硬件节点、运动控制服务全部是 Linux 的二进制。
Windows 就算装上 ROS 2，**也没有对应的机器人端硬件节点可以对话**。

### 2. 厂商的 ROS 驱动只按 Ubuntu 构建验证

- 强脑 `brainco_hand_ros2` 的官方系统要求写得很明确：
  **操作系统 Ubuntu 22.04，ROS 版本 ROS 2 Humble，Python 3.8+**。
- 半醒的 `bxi_revo2_example` 依赖 `bxi_ros2_pkg`，只在机器人自带的 Ubuntu 环境里提供。

厂商没在 Windows 上构建过、没验证过，就属于「未支持」，而不是「理论上不行」。

### 3. CAN 底层实现根本不同（这是最硬的一条）

| | Linux | Windows |
|---|---|---|
| CAN 实现 | 内核原生 **SocketCAN**（`can0` 就是个网络接口） | 没有系统级 CAN，只能靠转接器厂商的 **DLL**（ZQWL / ZLG 等） |
| 调用方式 | `socket()` + `bind()`，任何程序都能用 | 必须链接厂商闭源 SDK |
| 结果 | ROS 2 的 CAN 驱动直接可用 | 同一份 ROS 驱动代码在 Windows 上**没有 CAN 后端可挂** |

半醒用的是 FPGA 实现的 **PCIE 转 CANFD** 直控方案（`bxi_pci_drv`），
这条链路从驱动到用户态 API 整套是 Linux 的。

### 4. EtherCAT 在强脑 SDK 的支持矩阵里只有 Linux 打勾

强脑 Revo2 的三种通信接口中，**EtherCAT 只在 Linux 上有实现**。
而 EtherCAT 恰恰是高实时灵巧手控制最需要的接口。

### 5. 实时性调优在 Windows 上没有对应能力

Linux 侧可以做 **PREEMPT_RT 实时内核**、用 capabilities 提权、锁 CPU 亲和性、设线程调度策略。
Windows 对应的是内核驱动级别的实时扩展，成本极高，且厂商不会为工控场景提供。

## 三、能力边界总表

| 能力 | Windows | Ubuntu 22.04（双系统） |
|---|---|---|
| 灵巧手官方上位机（GUI 调试） | ✅ **只有 Windows 版** | ❌ |
| 灵巧手 Python / C SDK（485、CANFD 直连） | ✅ | ✅ |
| 灵巧手 EtherCAT 控制 | ❌ | ✅ |
| 灵巧手 ROS 2 驱动（`brainco_hand_ros2`） | ❌ 无 CAN 后端 | ✅ |
| 精灵 3 整机硬件节点 | ❌ | ✅ |
| 机器人端下发指令远程控制灵巧手 | ❌ | ✅ |
| 本体动作 + 手部动作融合 | ❌ | ✅ |
| 动作序列录制回放（整机） | ❌ | ✅ |
| ROS 2 Humble 本体运行 | ⚠️ 能装，但无机器人可连 | ✅ |

**一句话记忆**：
**Windows 管「一只手」，Ubuntu 管「一个机器人」。**

### 建议的推进顺序

| 阶段 | 做什么 | 环境 | 为什么这个顺序 |
|---|---|---|---|
| ① | 单只手接手上电、跑通官方示例 | Ubuntu（整机）或 Windows（独立） | 先证明硬件和接线没问题，隔离变量 |
| ② | 单手指令下发、读反馈（位置/电流/触觉） | Windows 独立调试最方便 | 上位机 GUI 直观，出问题好定位 |
| ③ | 机器人端下发指令远程控制手 | Ubuntu + ROS 2 | 打通 `/canfd_packet/rx` `tx` 链路 |
| ④ | 动作序列编排、录制与回放 | Ubuntu + ROS 2 | 在手能受控之后才有意义 |
| ⑤ | 本体动作 + 手部动作融合 | Ubuntu + ROS 2 | 需要同时调度本体与手，必须整机环境 |

## 五、为什么本项目最终必须落到 Ubuntu

因为**目标本身**决定了：

> 项目目标是「电脑远程控制机器人，驱动机器人手臂末端的灵巧手完成动作」。

这句里的「机器人」是精灵 3 整机，命令的发起端可以是电脑，
但**执行端必须有机器人硬件节点**，而硬件节点只在 Ubuntu 上跑。
Windows 无论怎么努力，都缺了执行端。

**所以：Windows 是「调试工位」，Ubuntu 是「生产环境」。两者不是二选一，是分工。**

## 六、双系统实操要点

> **先确认你真的需要装。** 整机联调的 Linux 侧可以落在两个地方：
> ① **机器人自带的机载 NUC**（出厂就是 Ubuntu 22.04 + ROS 2）—— 从 Windows
> **SSH 进去**即可跑通整条链路，**本机不需要装任何 Linux**；
> ② 你自己电脑的双系统 —— 只有在需要「本机发 ROS 2 话题远程控制」「本地看话题/录 bag/跑仿真」时才装。
>
> 两者不是二选一。装配后第一次联调的完整步骤见
> [`09-装配到机器人后的首次整机联调.md`](09-装配到机器人后的首次整机联调.md)。

| 事项 | 建议 |
|---|---|
| 分区 | 装 Ubuntu 前先在 Windows 里压缩卷腾出空间，**至少 100 GB**（ROS 2 + Gazebo + colcon 产物很吃空间） |
| 引导 | 用 Ubuntu 安装盘自动处理 GRUB，装完开机默认进 GRUB 菜单选择 |
| 时间 | 双系统常见坑：两边时间差 8 小时。在 Ubuntu 里执行 `timedatectl set-local-rtc 1` 可解决 |
| 显卡 | NVIDIA 独显在 Ubuntu 下装驱动后再跑 Gazebo，否则可能黑屏 |
| 文件互访 | Ubuntu 能直接挂载读写 Windows 的 NTFS 分区（默认只读，需要时 `ntfs-3g` 挂载） |
| 数据传递 | 优先走 Git 仓库；大文件走 U 盘或公司文件服务器 |

## 七、常见误解清单

| 误解 | 事实 |
|---|---|
| 「Windows 装不了 ROS 2」 | 官方有 Windows 二进制包。装得上，只是没有机器人可连 |
| 「装个虚拟机就行了」 | 虚拟机没有直通 CAN 硬件、没有实时性，EtherCAT 基本跑不通。做整机联调不可行 |
| 「用 WSL2 跑 ROS 2 总行了吧」 | WSL2 是完整 Linux 内核，ROS 2 能跑，但 **CAN 设备直通配置麻烦**；而且你要连的是外部机器人，仍需处理网络与 DDS 配置。可以作为过渡，不建议作为正式方案 |
| 「都在 Windows 上写代码，再拷到 Linux 跑」 | 编码 / 换行符 / 依赖版本全会出问题。用本仓库的 `.gitattributes` 统一换行符，通过 Git 同步而不是拷 U 盘 |
| 「ROS 2 的 Windows 支持是 Tier 1，应该没问题」 | 平台支持层级说的是 **ROS 核心**在 Windows 上被测试的程度，不代表**第三方硬件驱动**也在 Windows 上构建过。厂商没构建 = 没有 |
