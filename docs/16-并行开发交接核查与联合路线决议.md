## 3. 关键事实：`_hand` 变体**不是**灵巧手

本项同时更正本仓此前的一处记录。

**差异实测（`elf3_dof31` vs `elf3_dof31_hand`）**：

| 对比项 | 结果 |
|---|---|
| 文件 md5 | 不同 |
| **joint 名单 diff** | **完全为空**（35 个关节逐一同名同序） |
| **link 名单** | 均 36，**无任何名称含 `hand` 的 link**（`grep -o 'link name="[^"]*hand[^"]*"'` 返回空） |
| **唯一差异** | mesh 目录多 2 个文件：`l_hand.STL`、`r_hand.STL`（34 → 36） |
| 该 2 个 mesh 的引用 | 各被引用 2 次（visual + collision），挂在腕部末端 link 上 |
| `ros2_control` / `<transmission>` / `<gazebo>` / `<mujoco>` 标签 | **一个都没有**（`grep -c` = 0） |

**判定**：`_hand` 变体 = **外观上多一块固定手掌网格**，**没有任何手指自由度**。
这与官方规格描述一致 —— `Hands: Paid option, separate unit`（手是独立付费单元，不在本体上）。

**推论**：
1. 该 URDF **不能**作为「ELF3 + Revo2 联合仿真」的起点 —— 它没有可挂手的末端自由度，也没有控制器标签，直接进 Gazebo 无法做 `ros2_control`。
2. 因此「拿带臂 URDF + `ros2_control` 配置 + 6 行 xacro 固定关节焊上手」的路子，**前提不成立**。
3. 已跑通的联合路径是 **MuJoCo 侧离线合并**（`tools/revo2_merge_mjcf.py`，把 Revo2 MJCF 挂到 `r_wrist_z_joint`），
   端到端 `tools/revo2_pick_bottle_demo.py` 实测瓶子抬升 372.9 mm。

> 本仓此前在 `docs/14` 附近记录过「半醒已提供 ELF3+手 URDF，可不必从零拼」——
> 该表述过于乐观，以本节为准。

## 4. 「三个坑」的适用范围分类

交接方列出的三个坑，需按栈分类，不可照搬到 ELF3：

| 坑 | 适用范围 | 对 ELF3 是否成立 |
|---|---|---|
| 笛卡尔点 → IK → 臂手同步轨迹的**脚本骨架** | **通用** | ✅ 成立，可直接复用 |
| 时间戳必须为未来且递增 | **Gazebo / `ros_gz_bridge` 专属** | ❌ 不适用。`/tmp/sim.log` 中大量 `Detected jump back in time. Clearing TF buffer.` 即此坑现场；ELF3 走 MuJoCo，无 `/clock` 桥接 |
| 控制器容差要放宽 | **MoveIt / `ros2_control` 专属** | ❌ 不适用。ELF3 臂**不经 MoveIt**，走 `actuators_cmds_override` |
| IK 超时要改 | **MoveIt KDL 插件专属** | ❌ 不适用。同上 |

**即：三个坑中，两个半是 RM65 那条栈自身引入的，换到 ELF3 不会出现。**
交接清单中「哪些要重做：臂侧」的判断方向正确，但重做的工作量被高估了 —— 因为目标栈根本不同构。

另外，`/tmp/sim.log` 中另有 4 条实质 ERROR（与上述坑并列，交接清单未提）：


## 5. 联合路线决议

**否决「换到 RM65 替身」方向。** 理由：

1. **前提是误判** —— ELF3 仿真带臂且已被驱动（§2.2），替身没必要。
2. **目标栈不同构** —— RM65 走 MoveIt + `ros2_control` + Gazebo；ELF3 走 BXI 覆盖通道 + MuJoCo。
   在 RM65 上验证的臂侧配置（容差、IK 超时、时间戳对策）**一条都带不过来**。
3. **已有更近的成品** —— MuJoCo 侧「ELF3 + Revo2 右手」联合仿真已跑通抓水瓶（抬升 372.9 mm），
   且 Windows 与 Linux 两侧指标逐项一致，方案可复现。

### 建议路线

|---|---|---|
| 手侧（控制链路） | Revo2 话题 / 关节顺序 / 握力值 / 开合时序 —— 两线成果**互为交叉验证** | 已验证 |

- 手层 + 抓取：MuJoCo 联合模型抓水瓶（抬升 372.9 mm）

**下一交付目标**：在同一个仿真会话中完成「臂驱动到位 → 伸手 → Revo2 闭合 → 取起 → 递出」连续动作，
并用 `revo2_pick_bottle_demo.py` 自带的数值校验（瓶子抬升 / 最终高度 / 手部误差）自动验收。

### 6.2 清场命令的适用性评估

交接方给出的命令以进程名精确匹配（`-x`），**不会误杀发起者自身 shell**，比 `pkill -f` 安全，可采用。

**但需注意两点**：

1. `pkill -x ros2` 会终止**本机全部 `ros2` 进程**，不区分归属。若同一时刻另一条线有仿真在跑，会一并被杀。
   **多线共存时应改用明确 PID。**
2. 执行顺序建议为「先杀 launch 父进程 → 等待 3 s → 再逐个补杀子进程」。原因是父进程退出时的清理回调
   可能重新拉起部分节点，且父进程被 SIGTERM 时子进程不级联退出（详见 6.3）。

### 6.3 本线的清理记录（可复现的教训）

清理自 14:26 启动的 ELF3 仿真时实测：

```
kill -TERM 44933 44931 44893 44891   → 复查：44931（simulation）仍存活，PPID 已变为 1
kill -KILL 44931                     → 复查：已彻底退出
```

**结论：`lib/mujoco/simulation` 不响应 SIGTERM，且脱离父子关系后被 init 收养。**
若只发 SIGTERM 而不复查，该进程会以孤儿身份继续存在并**向同一话题重复发布**，
与下一次启动的实例形成冲突。**任何停仿真操作，结束后必须 `ps` 复查，必要时升级 SIGKILL。**
