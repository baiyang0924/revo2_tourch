# 上位机动作编辑：真实参数、存储机制与代码化对照

> **本文档解决一个问题**：不通过强脑官方上位机（BrainCo RevoII Hand Tool），
> 能不能直接编辑灵巧手动作？——**能**，而且上位机做的每一步都能用代码复现。
>
> **资料来源**：本机安装的上位机 `BrainCo_RevoII_Hand_Tool_win_0635_v0.0.19` 自身生成的
> 配置文件与日志（`settings.yaml`、`log/`），以及官方 wiki / SDK 文档。均为一手实测。
>
> - 阅读前提：先读 [`01-灵巧手硬件接线与上电操作手册.md`](01-灵巧手硬件接线与上电操作手册.md)
> - 协议细节：[`04-通信协议速查-Modbus与CANFD.md`](04-通信协议速查-Modbus与CANFD.md)

---

## 0. 结论速览

| 问题 | 答案 |
|---|---|
| 上位机是黑盒吗？ | **不是**。它是 Python + PySide6 打包的桌面程序，配置和日志都是明文 |
| 动作能不用上位机编辑吗？ | **能**。上位机的每个操作都对应一个协议层方法 |
| 动作存在电脑上吗？ | **不存**。动作序列写进**灵巧手自己的寄存器**里，按 `action_id` 回放 |
| 我们的代码能控制吗？ | 能。`src/revo2_standalone/` 直接走 Modbus，与上位机同一套寄存器 |

## 1. 上位机的真实工作参数

上位机把上次使用的连接参数写在自己的安装目录里，文件是 `settings.yaml`，
**可以直接用记事本打开查看**（路径：上位机安装目录下）。

以下为现场实测内容（已隐去无关项）：

```yaml
CONNECT_PARAMS:
  hand_version: 3        # 手版本：3 = Revo2 系列
  protocol_type: 2       # 协议类型：2 = Modbus

PROTOCOL_CONFIG:
  MODBUS:
    port: COM22
    baudrate: 460800     # ★ 与出厂默认一致
    timeout_s: 1
    device_id: 127       # ★ 右手 ID（左手为 126）
  ZQWL_CANFD:
    device_id: 126
    device_type: 42      # ZCAN_USBCANFD_200U（ZQWL / 智嵌 USB-CANFD 200U）
    channel: 0
    data_domain_baudrate: 5000kbps   # 数据域 5 Mbps（只支持 1M/2M/4M/5M）
    frame_type: false                # false = 扩展帧
    is_can: false                    # false = CANFD
    baudrate: 5000000
  ZQWL_CAN:
    device_id: 2
    device_type: 42
    channel: 0
    data_domain_baudrate: 1000kbps
    frame_type: true                 # true = 标准帧
    is_can: true                     # true = CAN
    baudrate: 1000000
```

### 从这份配置里能读出的四件事

1. **串口参数与我们的默认值完全一致** —— `460800` 波特率、设备 ID 126/127，
   说明 [`04`](04-通信协议速查-Modbus与CANFD.md) 里的波特率表与
   `src/revo2_standalone/revo2_modbus.py` 的 `DEFAULT_BAUD` 是对的。
2. **转接器是 ZQWL USB-CANFD-200U**（`device_type: 42`），走 `zlgcan.dll` 驱动。
   它同时支持 CAN 与 CANFD 两种模式，两种模式的波特率/帧型配置是分开的。
3. **CANFD 数据域是 5 Mbps**，仲裁域见 [`04`](04-通信协议速查-Modbus与CANFD.md) §3.3。
4. **`COM22` 是当时手所在的串口号**。串口号与 USB 插口绑定，换插口会变，
   每次接设备都应先确认端口（`tools/comm_diagnose.py --list-ports`）。

> **注意**：`settings.yaml` 只记录"上次用过的参数"，不是手当前的真实配置。
> 手侧的波特率/ID 存在寄存器 `1001` / `1002` 里，要读才知道（见 §5）。

## 2. 动作序列是怎么存的（重要）

### 2.1 机制

从软件的模块与方法命名可以看出，动作序列走的是**寄存器读写**，不是文件：

| 方向 | 方法（出现在上位机协议层中） | 作用 |
|---|---|---|
| 写 | `_write_action_sequence_count` | 写入动作条数 |
| 写 | `_write_action_sequence_data` | 写入动作数据（每一步的位置/时长） |
| 写 | `_write_action_sequence_cmd` + `set_action_cmd_id` | 按 ID 触发回放 |
| 读 | `_read_action_sequence_count` | 读回动作条数 |
| 读 | `_read_action_sequence_data` | 读回动作数据 |
| 读 | `get_action_sequence` | 取出完整序列 |

**关键结论：动作序列存在灵巧手内部，不存在电脑上。**

这解释了两个现场现象：

- 为什么上位机目录里**找不到任何动作文件**（没有 `.json` / `.yaml` / `.csv`）——
  它本来就不往磁盘存
- 为什么日志里会出现 `Failed to read action_step_params`——
  读的是**手里**的动作步参数，不是本地文件

### 2.2 ⚠️ 由此推出的两条操作纪律

**① 不要随手长按手背按键 5 秒。** 长按 = 恢复出厂设置，会把手 ID、波特率
**以及可能存放在手内的动作序列一并刷掉**。详见
[`01` §3.4](01-灵巧手硬件接线与上电操作手册.md)。

**② 辛苦调好的动作要做备份。** 既然动作只在手里，那么：

- 手返厂、固件升级、误触重置，动作就没了
- 用截图记录参数（如 `动作/喝水/参数.png`）是**有效的兜底**，但只记下了姿态，
  没有记下每一步的时长与顺序
- **更可靠的做法**：用代码把序列整体读回来存成 YAML/JSON（`_read_action_sequence_data`）。
  这一步现在受限于手的固件接口，待真机到手后验证（见 §6 待办）

## 3. 上位机能做的事，对应哪些接口

下表左侧是你在上位机界面上看到的元素，右侧是它在协议层对应的操作。
**看懂这张表，你就知道代码该怎么写。**

### 3.1 手动控制（Motor Status 页）

| 上位机元素 | 协议层方法 | 说明 |
|---|---|---|
| `positions` 行 | `set_finger_positions_intervals` | 位置 + 时间模式（对应我们代码的 `set_angles`） |
| `positions` 行（配速度） | `set_finger_positions_speeds` | 位置 + 速度模式 |
| `speeds` 行 | `set_finger_speeds` | 目标速度 |
| `pwms` 行 | `set_finger_pwms` | PWM 开环 |
| `currents` 行 | `set_finger_currents` | 电流环 |
| `target_interval` | `set_finger_position_interval` | 每指的插值时长 |
| `Hand Status` → Position | `get_actual_finger_positions` | 读回实际位置 |
| `Hand Status` → Speed | `get_actual_finger_speeds` | 读回实际速度 |
| `Hand Status` → Current | `get_actual_finger_currents` | 读回实际电流 |
| （状态汇总） | `get_actual_motor_status` | 一次取回 6 电机状态 |
| 触觉数据 | `_get_finger_touch_status` | **触觉版专用**：读指尖触觉 |

### 3.2 保护与量程参数

| 方法 | 用途 |
|---|---|
| `set_finger_max_current` | 单指电流上限 |
| `set_finger_max_speed` | 单指速度上限 |
| `set_finger_protect_current` / `set_finger_protection_current` | 保护电流（堵转保护） |
| `set_finger_position_range` / `_change_finger_limit_range` | **单指位置量程**（决定滑块上下限） |
| `_motor_data_unit_mode` | **数据单位模式**（见 §4） |

> 这几个参数是上位机界面里"能改但不起眼"的部分。**改之前先记原值**，
> 它们直接影响动作幅度的安全边界。台账记在 `config/hand_params.yaml`。

### 3.3 动作编辑（Action 对话框）

| 上位机元素 | 对应操作 |
|---|---|
| 动作步列表 | `_write_action_sequence_data` |
| 动作条数 | `_write_action_sequence_count` |
| `total_duration_ms` | 整段动作总时长（日志实测值：1001 / 1800 / 3200 / 11000 ms 等） |
| `total_interval_s` | 步间间隔（日志实测：1.5 或 2.5 s） |
| 执行（run） | `_write_action_sequence_cmd`，日志会打出 `run_idx: n, total: N` |
| 动作名 ↔ ID | `action_id` / `action_name` / `action_id_to_name` / `action_name_to_id` |

> 日志里出现过 `total: 2` / `total: 4` / `total: 10`——说明上位机支持
> **多步动作序列**（最多测到 10 步），并且会按索引逐步执行。

## 4. 单位与量程：0–100 是百分比，不是度

**这是最容易搞混的一点。**

上位机界面上你会看到两种数值：

| 位置 | 显示形式 | 含义 |
|---|---|---|
| 图形滑块上的数字（如 58 / 76 / 57） | 0–100 | **百分比**：占该关节全量程的比例 |
| `Hand Status` 表格里的 Position（如 95.9 / 29.6） | 0–100 | 同上（`X Axis Range: 200` 是绘图坐标，与量程无关） |

而**协议层与我们的代码用的是「度」**：

| 关节 | 位置上限（度） |
|---|---|
| 拇指 Flex | 59 |
| 拇指 Aux（Ad/Ab） | 90 |
| 食指 / 中指 / 无名指 / 小指 Flex | 各 81 |

上限定义在 `src/revo2_standalone/revo2_modbus.py` 的 `ANGLE_LIMITS`，
与 [`01` 附录 A](01-灵巧手硬件接线与上电操作手册.md) 对应。

**换算关系（大原则）**：`百分比 = 度数 ÷ 该关节上限 × 100`。
所以拇指 Flex 的 59° ≈ 100%，而同样是 100% 的拇指 Aux 则是 90°。

> ⚠️ **为什么这很重要**：
> 1. 你在上位机上抄下来的滑块数字是**百分比**，直接当度数写进代码会**偏小或偏大**，
>    而且不同手指的误差不一样，不会报错，只是动作不对。
> 2. 我们的代码有安全校验（超出 `ANGLE_LIMITS` 会拒绝执行）。
>    如果你把 95 当成度数传给拇指 Flex（上限 59），会被直接拦下 —— 这是保护，不是 bug。
> 3. `_motor_data_unit_mode` 这个接口说明上位机**可以切换单位模式**。
>    不同模式下同一个数字含义不同，**换模式后必须重新确认数值**。
>
> **首次接真机时，先做一次单位标定**：用极小幅度发一个已知值，看回读值，
> 反推当前是什么单位。别跳过这一步。

## 5. 日志里读出的真实故障案例（可直接抄进排障手册）

上位机把错误写进 `安装目录/log/YYYY-MM-DD/system_error.log`。
以下是本机历史上真实出现过的三类，**都是硬件/环境问题，不是软件 bug**：

### 案例 A：`zqwl_can.py:60 - 打开设备失败`

```
2026-09-07 15:42:39 | ERROR | zqwl_can.py:60 - 打开设备失败
```

**含义**：ZQWL 转接器打不开。常见原因：转接器没插、驱动没装、
或**被另一个程序占用**（上位机没关干净）。

### 案例 B：`Modbus Error: [Input/Output] No response received after 0 retries`

```
2026-09-08 14:04:26 | ERROR | modbus.py:58 - error reading registers:
Modbus Error: [Input/Output] No response received after 0 retries
```

**含义**：串口发得出、收不到。**这是"设备无响应"的标准形态**，
按 [`05` 故障排查手册](05-故障排查手册.md) 的第 1–3 层依次查
（供电 → 接线 → 波特率/ID 是否匹配）。

### 案例 C：`ClearCommError failed (PermissionError(13, '拒绝访问。'))`

```
2026-09-09 11:29:37 | ERROR | modbus.py:58 - error reading registers:
ClearCommError failed (PermissionError(13, '拒绝访问。', None, 5))
```

**含义**：**串口被别的进程占着**。Windows 串口是独占资源，同一时刻只能一个程序用。
典型场景：上位机还开着、或上一次没正常关闭。

**处理**：关掉所有可能占用串口的程序（尤其是上位机本体），必要时拔插 USB 重来。

> **这三条的价值**：以后你在代码里遇到"读不到手"，先对照这三个案例分类——
> 是**打不开**（驱动/占用）、**发得出收不到**（参数/接线）、还是**被占用**（进程冲突）。
> 定位方向完全不同，别混着试。

## 6. 在不接硬件的情况下能做什么

机器人返厂期间，以下工作**完全不依赖硬件**，可以先做完：

| 可以现在就做 | 说明 |
|---|---|
| 精读本文档 + [`01`](01-灵巧手硬件接线与上电操作手册.md) | 建立完整心智模型，接上真机就不会瞎试 |
| 跑通无硬件演练 | `python src/revo2_standalone/01_selfcheck.py --dry-run`，以及所有 `--print-only` |
| 用配置驱动搭动作库 | 编辑 `config/gestures.yaml`，改成从**百分比**换算来的度数（见 §4） |
| 写新动作 | 参考 `src/elf3_ros2/config/sequences.yaml` 的格式，先写、先预览 |
| 准备参数台账 | 把 `config/hand_params.yaml` 按附录 A 填好，真机一到直接比对 |
| 整理排障清单 | 把 §5 三个案例补进 [`05`](05-故障排查手册.md) 的速查表 |

**接上真机后的第一件事**（顺序不能换）：

```
① 确认手的串口号（换插口会变）
② 读寄存器 1001 / 1002，确认真实波特率与协议
③ 极小幅度试动作，反推单位模式（度还是百分比）
④ 通过后再导入动作库
```
