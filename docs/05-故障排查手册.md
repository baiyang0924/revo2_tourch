# 故障排查手册

> 通信报错、设备无响应怎么查。**按顺序走，不要跳步、不要猜。**
> 每一节都是「我怎么判断它是不是这个原因 → 是的话怎么修」。

---

## 0. 排查总原则

三条铁律，违反任何一条都会让你多花几小时：

1. **一次只改一个变量**。同时换线、换 ID、换波特率，就算好了你也不知道是哪个起的作用。
2. **先分层，再定位**。通信链路是分层的，按「供电 → 物理接线 → 参数匹配 → 软件环境 → 应用逻辑」
   从上往下查，**上层的问题不要在下层找**。
3. **先做无风险的验证**。用「读固件版本」「读实际位置」这类只读操作判断通路，
   别一上来就拿运动指令试。

### 分层模型

```
第 5 层  应用逻辑      我的抓取代码/动作序列写得对不对
第 4 层  软件环境      ROS_DOMAIN_ID、RMW 实现、SDK 版本、conda 干扰
第 3 层  参数匹配      设备 ID、波特率、master_id、总线号
第 2 层  物理接线      A/B 是否接反、CAN_H/CAN_L、终端电阻、插到底没有
第 1 层  供电          电压够不够、电流能力够不够、黄灯/红灯
```

**排查方向永远是从第 1 层往上，不是从第 5 层往下找。**

## 1. 第一分钟：看灯

**上电后先只看两个东西：手背灯 + 手指动不动。**

| 灯效 | 判定 | 跳到 |
|---|---|---|
| 🟢 绿灯常亮 + 手指已张开 | 供电、复位、自检全部通过 | 转第 3 节（通信） |
| 🟢 绿灯一直闪烁 | 复位 / 位置校准没完成 | 第 2.2 节 |
| 🟡 黄灯闪烁 | **供电过低** | 第 2.1 节 |
| 🔴 红灯常亮 | 硬件异常 | 第 2.3 节 |
| 🔵 青灯常亮 | OTA 升级中 | **不要断电**，等结束 |
| 完全不亮 | 没有供电 | 第 2.1 节 |

## 2. 供电层

### 2.1 完全不亮 / 黄灯闪烁

**判断依据**：黄灯闪烁官方定义为「供电过低」，说明有电但电压不够。

**排查顺序：**

| 步 | 动作 | 期望结果 |
|---|---|---|
| 1 | 检查 XT30 接头是否**插到底**（XT30 有防呆方向，容易只插一半） | 插到底有明确手感 |
| 2 | 独立调试：检查电源适配器开关 / 插排开关是否打开 | 开关到位 |
| 3 | 用万用表量**灵巧手输入端**（不是电源输出端）的电压 | 基础版 12–28V；进阶/触觉版 12–64V |
| 4 | 量**负载状态下**的电压（手指运动时再量一次） | 不应明显低于额定值 |
| 5 | 整机接入：确认机器人已正常启动、硬件节点已拉起 | 机器人电机灯亮 |
| 6 | 换一根电源线 / 换一个电源试 | 灯正常 |

**为什么强调「负载状态下量」**：空载电压正常、一带负载就掉，
典型是电源电流能力不足或线缆压降太大。
灵巧手最大电流可达 **4.65 A @24V**，一个 1A 的小电源带不动。

**为什么强调「量手这一端」**：线长、线径、接触电阻都会产生压降。
量电源端正常、量手端偏低，说明问题在线缆上，不在电源上。

### 2.2 绿灯一直闪烁（复位 / 校准卡住）

位置校准要求手指**能自由运动到起始位置**。卡住的原因通常是：

| 原因 | 处理 |
|---|---|
| 手指被外部挡住 / 卡住 | 清空手指周围，重新上电 |
| 手正攥着物体 | **必须松开**。校准期间所有手指会张开，抓握状态会顶住 |
| 手指内部有异物 | 断电检查，不要强行掰 |
| 结构受过冲击 | 联系售后 |

处理：断电 → 清障 → 重新上电 → 观察绿灯是否转常亮。

### 2.3 红灯常亮

1. 先断开电源，等 10 秒，重新上电（排除偶发）。
2. 仍红灯 → 记录现象（灯效、是否有异响、是否在某动作后出现），**联系售后**。
3. 不要自行拆解——官方注意事项第 10 条明确写了私自拆解会导致保修失效。

## 3. 物理接线层

### 3.1 485 接线的三个高频错误

| 错误 | 现象 | 修法 |
|---|---|---|
| **A/B 接反** | 完全不通，或偶发乱码 | A 接 A、B 接 B（不同模块丝印命名可能相反，接不通就对调试一次） |
| **终端电阻缺失** | 短线能通、长线不通，或距离一长就丢包 | 总线首尾各加 120Ω |
| **共用 GND 缺失** | 偶尔通、偶尔不通 | 485 虽然是差分，现场干扰大时把两端 GND 也接上 |

### 3.2 CANFD 接线的四个高频错误

| 错误 | 现象 | 修法 |
|---|---|---|
| **仲裁域波特率不是 1 Mbps** | 完全不通 | 官方规定**固定 1 Mbps**，不要改 |
| **数据段波特率不匹配** | 完全不通 | 手默认 5 Mbps（寄存器 `1002`），核对转接器设置 |
| **终端电阻缺失** | 偶发丢帧 | 两端 120Ω |
| **CAN_H / CAN_L 接反** | 完全不通 | 对调 |

### 3.3 整机接线的两个高频错误

| 错误 | 现象 | 修法 |
|---|---|---|
| **左右手接反**（左手插 CAN6、右手插 CAN5） | 终端可能一直刷数据但**手指不动**；或报「读取超时」 | 左右对调。**接反不会烧硬件**，放心试 |
| **线缆被关节卡住 / 绷紧** | 手臂运动时手偶尔掉线 | 重新理线，留出活动余量 |

> ⚠️ 注意：**进阶版和触觉版没有协议拨码开关**（那是基础版才有的）。
> 如果你的排查清单里有「检查拨码开关」，画掉它，别浪费时间拆手腕件。

### 3.4 接线自检清单（动过线就过一遍）

- [ ] 供电插到底，无松动
- [ ] 手端实测电压在型号额定范围内
- [ ] 左手 → CAN5，右手 → CAN6
- [ ] 差分线极性正确（A/B 或 CAN_H/CAN_L）
- [ ] 两端终端电阻已装
- [ ] 线缆没有被关节夹住、没有绷紧
- [ ] 手腕法兰螺钉旋入深度 < 3 mm

## 4. 参数匹配层

三个参数必须**三方一致**：设备端、物理接线、程序里写的。

| 参数 | 左手默认 | 右手默认 | 改在哪 |
|---|---|---|---|
| 设备 ID | 126（`0x7E`） | 127（`0x7F`） | 寄存器 `1000` |
| 总线（整机） | CAN5 | CAN6 | 程序里的 `init_bxipci_device(总线, ID, ...)` |
| master_id | 1 | 1 | 程序参数 |
| RS485 波特率 | 460800 | 460800 | 寄存器 `1001` |
| CANFD 数据段波特率 | 5 Mbps | 5 Mbps | 寄存器 `1002` |

**高频事故：误触「长按 5 秒恢复出厂设置」** → ID、波特率全部回到默认，
如果现场本来改过参数，整条链路就失配了。
症状：昨天还好，今天完全不通，且没人改过程序。

**排查方法**：改回默认参数试；或用官方上位机（能自动扫描）连上看实际 ID。

**参数台账**：每次现场调通后，把实际参数记到 `config/hand_params.yaml`。
下次出问题一对比就知道是不是参数被改了。这是最省时间的习惯。

## 5. 软件环境层（整机 / ROS 2）

### 5.1 `ROS_DOMAIN_ID` 不一致 —— 整机排名第一的坑

**原理**：机器人硬件节点跑在 **root** 用户下，你的程序跑在普通用户下。
ROS 2 靠 `ROS_DOMAIN_ID` 划分通信域，两边不一致就完全是两个世界，
`ros2 topic list` 什么都看不到。

**症状**：`ros2 topic list | grep canfd_packet` 没有任何输出。

**排查：**

```bash
# ① 看服务文件里写没写
grep -r ROS_DOMAIN_ID /etc/systemd/system/ 2>/dev/null

# ② 逐个试，哪个能列出话题就是哪个
for id in 0 22 30 31 32; do
  ROS_DOMAIN_ID=$id RMW_IMPLEMENTATION=rmw_cyclonedds_cpp ros2 topic list 2>/dev/null \
    | grep -q canfd_packet && echo "正确的是 DOMAIN_ID=$id"
done
```

官方规则：**遥控器启动 = 30 + 机器人序号；App 启动固定 22**。

> ⚠️ **最常见的写法错误**：在普通用户终端设好变量再 `sudo su` 切到 root。
> `sudo su` **不会继承**这些环境变量。**必须在 root shell 里重新 export。**

正确做法：

```bash
sudo su
export ROS_DOMAIN_ID=<确定的值>
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export ROS_LOCALHOST_ONLY=0
export CYCLONEDDS_URI='<CycloneDDS><Domain Id="any"><General><Interfaces><NetworkInterface name="lo" multicast="true"/></Interfaces><AllowMulticast>true</AllowMulticast></General></Domain></CycloneDDS>'
```

### 5.2 环境没 source（顺序也有讲究）

```bash
# 正确顺序：先 ROS，再厂商包，最后自己的工作空间
source /opt/ros/humble/setup.bash
source /opt/bxi/bxi_ros2_pkg/setup.bash
source ~/bxi_ws/bxi_revo2_example/install/setup.bash
```

**顺序错了的后果**：后 source 的会覆盖前面的环境变量，可能把手写的包路径盖掉。

**典型报错对照：**

| 报错 | 原因 | 修法 |
|---|---|---|
| `communication.msg.CANFDPacket not found` | 没 source 厂商消息包 | `source /opt/bxi/bxi_ros2_pkg/setup.bash && source install/setup.bash` |
| 缺 `stark-sdk.h` / `libbc_stark_sdk.so` | 没下载 C++ SDK | 在示例包目录 `./download-lib.sh` 后重新 `colcon build` |
| `No module named bc_stark_sdk` | SDK 没装 / 装错环境 | `pip install bc-stark-sdk==1.5.1 --index-url https://pypi.org/simple/` |
| `ModuleNotFoundError` 但明明装过 | **装进了 conda 环境** | 退出 conda（`conda deactivate`）后用系统 Python 重装 |

> ⚠️ `bc-stark-sdk` 官方指定版本是 **1.5.1**，别装最新版。
> 且要装在**系统 Python**，不要装在 conda 里。

### 5.3 两个进程抢同一只手

**症状**：随机性无响应、偶发超时、动作跳变。

**原因**：同一只手同时只能有一个程序控制。两个进程同时写同一条总线会互相干扰。

**排查：**

```bash
# 看有哪些节点在跑
ros2 node list
# 看有没有别的进程占用
ps aux | grep -i revo
ps aux | grep -i stark
```

**修法**：关掉多余进程。开发时养成习惯：跑程序前先确认没有残留进程。

## 6. 应用逻辑层

| 症状 | 原因 | 修法 |
|---|---|---|
| 手指方向反了 | 下发的值语义搞反（以为值大=张开，实际=弯曲） | 先用单指、极小幅度试方向，确认后再放开行程 |
| 手指动一下就不动 | 保护电流偏小，反复触发堵转保护 | 检查寄存器 `930`–`935`（默认 500 mA，范围 100–1500 mA） |
| 报超范围拒绝写入 | 单位模式不一致 | 检查寄存器 `937`：`0` 归一化 / `1` 物理单位。**单位搞错会下发超范围值** |
| 手指抖动 / 异响 | 参数不合适，或负载超规格 | 核对规格：单指捏力 ≥15N、整手负载 ≥20kg、屈伸速度 ≤0.65s |
| Turbo 模式不生效 | Turbo **掉电后恢复默认关闭** | 重新开启寄存器 `1065` |
| 关机后参数全没了 | **这是正常行为** | 手指最大/最小位置、最大速度/最大电流、保护电流在关机或重启后都会恢复默认值。需要持久化的参数要在程序启动时重新写入 |
| 动作卡在中间 | 期望时间设置不合理 | 寄存器 `1010` 的期望时间范围 **1 ~ 2000 ms** |
| 触觉数据读不到 | 触觉开关没打开 / 型号不匹配 | 电容式开关 `4000`–`4004`，压阻式 `6130`–`6134`；先用 `970` 读触觉厂商类型确认 |

## 7. 通信诊断工具

仓库里提供了 `tools/comm_diagnose.py`，按上面的分层模型逐层自检并输出报告：

```bash
python tools/comm_diagnose.py              # 全部检查
python tools/comm_diagnose.py --layer 1    # 只查供电层
python tools/comm_diagnose.py --layer 3    # 只查参数/串口层
```

它做的是**只读探测**，不会发运动指令，可以放心在真机上跑。
